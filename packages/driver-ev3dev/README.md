# @spinecord/driver-ev3dev

The contract `Provider` for a LEGO EV3 running [ev3dev](https://www.ev3dev.org) (ev3dev-stretch). It emits the same device kinds, ids, channels and commands as the stock-firmware driver, so a model sees the same robot whichever firmware the brick runs.

Two halves:

| File                      | Runs on      | What it is                                                                                                             |
| ------------------------- | ------------ | ---------------------------------------------------------------------------------------------------------------------- |
| `bridge/ev3dev_bridge.py` | the brick    | One Python file, standard library only, in the syntax of Python 3.5 (what ev3dev-stretch ships). JSON lines on stdin/stdout, hardware through sysfs. Owns the safety rules. |
| `src/provider.ts`         | the computer | `Ev3devProvider implements Provider` over a `LineTransport`. No I/O of its own.                                        |
| `src/ssh.ts`              | the computer | `SshLineTransport` (the system `ssh` client), `installBridge()`, `ProcessLineTransport`.                               |
| `scripts/smoke-ssh.ts`    | the computer | Read-only check of a real brick.                                                                                       |
| `test/fake-brick.ts`      | tests        | A fake sysfs tree; the real bridge runs against it with the local Python.                                              |

Tests: `bun test` in this folder (needs a local `python3` or `python`; without one the brick tests are skipped with a message). Typecheck: `bun run typecheck`.

## Using it

```ts
import { Ev3devProvider, SshLineTransport, installBridge } from "@spinecord/driver-ev3dev";

const ssh = { host: "ev3dev.local", user: "robot" }; // port, identityFile, options are optional
await installBridge(ssh); // copies the bridge to ~/spinecord/ev3dev_bridge.py
const ev3 = new Ev3devProvider(new SshLineTransport(ssh), {
  limits: profile.limits, // required: the robot profile's limits
  hardware: myDeployment.ev3dev.hardware, // required: { low_battery_v, max_tone_ms, speech_volume_pct }
  pair: { left: "B", right: "C" }, // optional: only for a robot with a motor pair; `ev3.pair` exists only then
});
const devices = await ev3.devices();
await ev3.command("ev3.pair", "run_pair", { left_deg: 40, right_deg: 40, speed_pct: 30, brake: false }, signal);
await ev3.close(); // stops the heartbeat; the brick brakes
```

`limits` and `hardware` are required; a missing or non-positive field throws `RuntimeError("misconfigured")`. `EXAMPLE_EV3DEV_HARDWARE` is a documented example and is never applied by itself. Other options: `id` (default `ev3`), `pair` (no default: without it the bridge's hello carries none and there is no `ev3.pair`), `roles`, `heartbeatMs` (300), `helloTimeoutMs` (60000, covers the ssh handshake and Python start), `requestTimeoutMs` (2000), `linkSilenceMs` (3000), `stopLinkMs` (700).

### ssh

`SshLineTransport` spawns `ssh` with an argument array (no shell on the computer), so it works with OpenSSH on macOS, Linux and Windows 10+. It runs `python3 -u <remote path>` on the brick. It uses `BatchMode=yes`: the brick must accept a key (ssh never prompts for the password), and the brick's host key must already be known. The repository README has the commands that set both up ("An EV3 on ev3dev: the ssh key first"). `host`, `user`, `port` and the remote path are checked against plain character sets because ssh and the remote shell parse them. `installBridge()` sends the file through ssh's stdin (no scp), writes to a temporary name, renames, and compares the byte count.

## Safety, as built

- **One command = one operation**, bounded by time on the brick: at most `maxOpMs` of motion (default and ceiling `MAX_MOTION_MS` = 3000 ms, never above `limits.max_command_ms`; the bridge has the same ceiling and ignores a larger value). It can be that long because the brick has its own watchdog, and one long operation avoids chaining coasting chunks over a slow link. Motion uses only `run-to-abs-pos` and `run-timed`; `run-forever` and `run-direct` are never written. The kernel ends `run-timed` by itself after `time_sp`. It ends `run-to-abs-pos` only when the motor arrives: ev3dev has no time limit for a position move, so a wheel that cannot arrive (blocked) pushes until `stop` is written. The bridge writes it at the time bound, the watchdog on silence, and the guard (below) when the bridge process itself is gone. A degree move is sent as an absolute target: the encoder position read at the start of the operation plus the delta, capped to what fits in the time bound. `run-to-rel-pos` is not used: on a real brick it counts from the previous target, not from the motor's position, so a relative move sent after a coasting overshoot runs backward (`test/provider.test.ts` checks the absolute target after an overshoot). A degree target that has not arrived at the time bound is braked and reported with reason `timeout` and `measured.time_limited: true`. The provider never chunks; the runtime does.
- **Watchdog on the brick**: with no line for 1000 ms, or when stdin closes, or on SIGTERM/SIGHUP/SIGINT, the bridge writes `stop_action=brake` and `command=stop` to every tacho motor. The provider sends a heartbeat every 300 ms. Worst case after the computer or the link dies mid-move: the motors are braked 1000 ms after the last message.
- **Guard on the brick**: the bridge starts a second, tiny Python process (`python3 -S -c`, standard library, no file of its own) whose stdin is a pipe from the bridge. When the bridge process ends in any way, `SIGKILL` and the kernel's out-of-memory killer included, the pipe closes and the guard writes `stop_action=brake` and `command=stop` to every tacho motor, then exits. `hello.guard` says it is running (`hello.guard_pid` is its process id); the provider refuses a brick where it could not be started (`misconfigured`, with `hello.no_guard` as the reason). The bridge looks at the guard on every pass of its main loop (at least every 10 ms): when the guard is gone while the bridge lives, the bridge brakes every motor, sends `{"ev":"guard_lost"}` and ends, so the link closes and the next one starts a bridge with a guard. While a motor runs on unregulated power (`power`, a loop's outputs: the kernel's `run-direct`, which has no time limit) the guard is also a deadman: the bridge writes it one byte on every pass of its main loop, and a guard that reads nothing for `GUARD_DEADMAN_MS` (250 ms) brakes every motor. The bridge never writes `run-direct` without first arming it. What nothing here covers: a bridge that hangs during any other move (the watchdog and the look at the guard run in its own main loop) and a brick whose kernel or power fails.
- **Loops on the brick** (bridge version 7, CONTRACT §5a): a loop is one task of the bridge's scheduler, with absolute deadlines, ticking beside the watchdog and the guard's feed. It opens every sysfs attribute it reads or writes once and reads and writes them through those descriptors (`pread`/`pwrite` at offset 0), runs the law in a Python port that `test/law_check.py` holds to `packages/protocol/loop-golden.json`, and keeps Python's garbage collector off while it runs. A `power` output writes `duty_cycle_sp` on every tick and the bridge sets it to 0 `hold_ms` after the latest refresh; a `run_time` output writes `speed_sp` and `run-timed` with `time_sp` = `hold_ms`, so the kernel ends it. Every end brakes the driven motors first, then sends `loop_end`. `probeLoop()` measures the tick's cost on the brick (`loop_probe`) and sets the link's `max_rate_hz`; 50 until then. The provider asks for version 7 only for a loop and for `power`: on an older bridge they are absent from the manifest and a loop is refused with `misconfigured`, naming `--install-bridge`; everything else keeps working.
- **Stop** writes the brake to every motor first, then waits up to 800 ms until every motor is not `running` and reads `speed` 0. `stop_worst_ms` = 800 + `stopLinkMs`. With the link closed, `stop()` throws `robot_offline` because nothing can be verified.
- **Few lines, timely looks.** Reads issued in the same turn (one read of every device) leave as one `read_many` line and come back as one; a read that may switch a sensor mode goes alone. The bridge must be version 4 or newer (`hello.bridge`): an older one fails at `hello` with `misconfigured` on every connection attempt until the bridge is reinstalled: `--install-bridge` on the server's command line, `"install_bridge": true` in its config file, or `installBridge()` from code. While an operation runs, the bridge looks at the motors right after the command, then at half the time the target still needs, between 2 ms on arrival and the 10 ms tick far from it; the main loop still wakes every 10 ms for the watchdog and the touch sensors.
- **Never backward.** The position is read immediately before the target is written and again immediately before the command. If the motor is already past the target and still rolling the commanded way (it was coasting from the previous operation), no run command is written: the operation ends as completed with the measured travel, braking if `brake` is true. Covered by `test/coasting_check.py`.
- **Coasting.** With `brake: false` the motor is still turning when the command returns. `measured` is the encoder change from the position read at the start of the operation to the moment of return, not where the motor comes to rest; the next operation starts from wherever the motor is by then. End a coasting sequence with a braking operation or `brake{}`.
- **Speech is bounded and cut like motion.** `speak` runs `espeak ... --stdout -- <text> | aplay -q` as two child processes started from argument lists (no shell; `--` keeps a text that starts with `-` from being read as options). One phrase at a time (`busy` otherwise), at most 200 characters and 15 s: a phrase still playing then is killed and reported with reason `timeout`. `abort`, `stop`, the watchdog and the end of the bridge (stdin closed, signal) kill `aplay` first, then `espeak`. Only a `SIGKILL` of the bridge itself can leave a phrase playing to its end (the guard brakes motors, it does not cut audio).
- **Reads never write.** A sensor channel of another mode comes back `null` with error `mode_switch_required` unless the read names it and passes `allow_mode_switch`; a switch updates the `active` flags and calls `onDevicesChanged` listeners.

## Device mapping

| Device                           | ev3dev source                                                   | Notes                                                                                                                                                                                                                                                                                                                                  |
| -------------------------------- | --------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ev3.A`..`ev3.D` motor           | `/sys/class/tacho-motor/motorN` by `address`                    | degrees = counts x 360 / `count_per_rot`; speed percent = share of the motor's own `max_speed`. `stalled` = the last operation moved under 0.5 degrees when 4 or more were expected by its end.                                                                                                                                                   |
| `ev3.pair` motor_pair            | the two motors of the declared `pair`; absent without one       | See below.                                                                                                                                                                                                                                                                                                                             |
| `ev3.S1`..`ev3.S4`               | `/sys/class/lego-sensor/sensorN` by `address` and `driver_name` | The bridge's `SENSORS` table says, per driver, which mode and values each channel is. EV3: touch `TOUCH`; color `COL-REFLECT`, `COL-AMBIENT`, `COL-COLOR`, `RGB-RAW`; ultrasonic `US-DIST-CM` scaled by `decimals`; gyro `GYRO-ANG`, `GYRO-RATE`, negated to counter-clockwise-positive; infrared `IR-PROX`, `IR-SEEK` (heading negated: positive = beacon to the left), `IR-REMOTE`, both on the channel hello's `ir_channel` names. NXT: `lego-nxt-touch`, `lego-nxt-light` (`REFLECT`, `AMBIENT`), `lego-nxt-sound` (`DB`, `DBA`), `lego-nxt-us` (`US-DIST-CM`), `lego-nxt-temp` (`NXT-TEMP-C`). Any other driver is kind `sensor`: `values` (the `num_values` values of the current mode, scaled by `decimals`, in `units`), `mode`, `set_mode`, and `send` when the driver lists `commands`. A mode the sensor does not list in `modes` gives a null reading that names the modes it has. |
| touch `presses`                  | counted by the bridge                                           | ev3dev has no bump-count mode; the bridge samples the button about 50 times a second.                                                                                                                                                                                                                                                  |
| any other motor driver, a sensor off `in1`-`in4` | —                                                               | Listed as kind `unknown` with its driver name; never skipped.                                                                                                                                                                                                                                                                          |
| `ev3.speaker`                    | the `beep` program; `espeak` and `aplay` for `speak`            | `tone` and `beep` have no volume control; without `beep` on the brick they fail with `unsupported` and the description says so. `speak{text, voice?, rate_wpm?}` is declared only when the bridge finds `espeak` and `aplay` at hello (ev3dev-stretch ships both); `voice` is an enum read from `espeak --voices` once per bridge process (default `es-la`, else `en`), the loudness is `hardware.speech_volume_pct`. Without them the speaker has no `speak` and its description says why. |
| `ev3.display`                    | —                                                               | Listed, but `text` and `clear` always fail with `unsupported`: the brick's menu owns the framebuffer.                                                                                                                                                                                                                                  |
| `ev3.led`                        | `/sys/class/leds/led{0,1}:{red,green}:brick-status`             | Both sides together. flash and pulse use the kernel `timer` trigger; the stock double pulse is not reproduced.                                                                                                                                                                                                                         |
| `ev3.buttons`                    | `EVIOCGKEY` on `/dev/input/by-path/platform-gpio_keys-event`    | The brick's menu reacts to the same buttons.                                                                                                                                                                                                                                                                                           |
| `ev3.battery`                    | `/sys/class/power_supply/*/voltage_now`                         |                                                                                                                                                                                                                                                                                                                                        |

### run_pair precision

The bridge writes both motors' setpoints, then the two `command` files one after the other, with `speed_sp` in proportion to each motor's travel so both need the same time. That is all the synchronization there is: the starts are a few milliseconds apart (two sysfs writes from Python on the brick's CPU) and each motor regulates its own speed, so a wheel under more load lags during the move and the other does not wait for it, unlike the stock firmware's synchronized opcode. Each motor still aims at its own encoder target. A wheel whose proportional speed would fall under 10 counts/s is run at 10. Read `measured.left_deg` and `measured.right_deg`.

## Bridge protocol

One JSON object per line. Device names are local (`B`, `pair`, `S4`, `battery`).

| Request                                                                                                           | Reply                                                                                                                                    |
| ----------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `{"op":"hello","id","config":{"bounds":{max_speed_pct,max_op_ms,low_battery_v,max_tone_ms,speech_volume_pct},"pair"?:{left,right},"ir_channel"?:1-4}}` (`pair` only for a robot with a motor pair, `ir_channel` only for a channel other than 1) | inventory: `bridge` (version), `guard` (the guard process is running; `guard_pid`; `no_guard` says why not), `ir_channel`, `motors`, `sensors` (with raw `driver_name`, `mode`, `modes`; a generic one also `num_values`, `units`, `commands`), `unknown`, `ports`, `capabilities`, `speech` (`voices`, `default_voice`, limits; null with `no_speech` saying why), `watchdog_ms`, `max_op_ms` |
| `{"op":"read","id","device","channels","allow_mode_switch"}`                                                      | `readings:[{channel,value,error?,absent?}]` (`absent: true` = the sensor answered that it sees nothing, e.g. no beacon), `mode` for sensors, `num_values` and `units` for a generic one                                                                                  |
| `{"op":"read_many","id","reads":[{device,channels}]}`                                                             | `results:[...]`, one per read in order: what `read` answers for it alone (`ok`, `readings`, `mode`, or `ok:false`, `code`, `message`). Never switches a sensor mode |
| `{"op":"command","id","device","command","args"}`                                                                 | `result:{measured,clamped,reason,ms}`                                                                                                    |
| `{"op":"abort","target":<command id>}`                                                                            | none; the command (a motion or a `speak`) answers with reason `preempted`; a loop (`target` = its id) ends with `loop_end` reason `preempted`                                                                |
| `{"op":"loop_start","id","plan"}` (a `LoopPlan` with local device names) | `loop` (its id, the request's id); then `{"ev":"loop","loop",ticks,overruns,age_ms,periods,signals,outputs,trace,params}` after 20 ticks and every 0.5 s (windows since the previous line), and one `{"ev":"loop_end","loop","reason","guard"?,"brake_error"?,"failure"?,...}` with the last window |
| `{"op":"loop_set","id","loop","params","ramp_ms"}` | `params` (as the law holds them); the change lands on the next tick |
| `{"op":"loop_probe","id","plan","ticks"}` | `probe:{ticks,signals,outputs,mean_ms,p50_ms,p99_ms,max_ms,max_rate_hz,python}`: the plan's ticks back to back with every output written as 0 and no run command |
| `{"op":"stop","id"}`                                                                                              | `motors_stopped`, `detail` when false                                                                                                    |
| —                                                                                                                 | `{"ev":"guard_lost"}` when the guard process ended; the bridge has braked every motor and ends                                           |
| `{"op":"hb"}`                                                                                                     | `{"ev":"hb"}`                                                                                                                            |

Errors are `{"id","ok":false,"code","message"}` with contract error codes. `--root DIR` (or `SYSFS_ROOT`) points the bridge at another tree; tests use it.

## Smoke check on a real brick

```
bun scripts/smoke-ssh.ts --host <host> --user robot [--port 22] [--identity <key file>]
```

Installs the bridge, then prints the inventory and one read of every device as JSON. The transport is wrapped by `readOnlyTransport`, which throws on anything but `hello`, `read`, `read_many` and `hb` and on reads that switch a sensor mode, so the script cannot move the robot. When the script closes the link, the bridge does what it always does on a closed link: it writes brake and stop to the (idle) motors.

## Not verified on hardware

Bridge version 4 ran on a brick on 2026-11-22, on its Python 3.5.3: connect, stop, the square, `kill -9` of the bridge and the guard (`docs/hardware-log.md`, with the checklist of what to run). Version 5 is version 4 plus a hello that may leave out `pair` (the provider asks for version 5 only when it sends no pair, and for version 4 otherwise). Version 6 is version 5 plus the NXT sensors, generic sensors and `ir_channel` (the provider asks for version 6 only when the robot file's `ir_channel` is not 1; on an older bridge the NXT and other sensors are `unknown`, with a description that names version 6). Version 7, the one in this folder, is version 6 plus loops on the brick, the `power` command, `drives` and the guard's deadman. None of the three has run on a brick. Everything else here is tested against the fake tree with the computer's Python.

To confirm on a brick:

- the exact mode names and `decimals` per sensor;
- that `state` shows `running` right after a command write, and `speed` reads exactly 0 at rest;
- chained coasting operations, and how smooth coasting chunks are over an ssh round trip;
- brake overshoot against the 3-degree arrival tolerance;
- the 0.1 s wait after a mode switch, and the gyro reset by mode switch;
- the `EVIOCGKEY` button read;
- write permission of the ssh user on the LED `trigger` files;
- the guard process: that a second `python3 -S` starts within the hello timeout and fits in the brick's memory next to the bridge, and that it brakes a motor mid `run-to-abs-pos` when the bridge is killed with `kill -9`;
- the sign of `IR-SEEK`'s heading (taken from the sensor's documentation: negative to the left);
- the values of `IR-SEEK` and `IR-REMOTE` for channels 2-4, and the NXT and generic sensors' `num_values`, `units` and `commands` on a real driver.
