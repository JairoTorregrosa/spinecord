# Contract v3 (2026-11-22): spinecord MCP

Audience: the model (Claude Fable 5.2) and the people who extend the robot. English only on the MCP surface.

Sources of truth, in this order: this file → `packages/protocol/types.ts` (types, FSM transition tables) → `packages/protocol/tools.ts` (tool names, descriptions, input and output schemas, server instructions, served verbatim).

spinecord runs on one computer: one bun process (`apps/local`) that serves MCP over stdio and holds the runtime (§4) and the providers of its robots. An MCP client starts it. It stores nothing.

## 0. Principles

1. **Generic primitives, no use cases.** A robot is a set of devices. A device self-describes its channels (what can be read) and commands (what it can do). The tool set is fixed; extending the robot means adding a device manifest, never a tool. A behavior that must react faster than a model turn is data handed to a generic primitive: a condition (`until`), a program (§5) or a loop (§5a). No tool, node or law names a use. A device may live in a browser page that a person opens (§2.4): the page declares its manifests, and the same fixed tools reach it.
2. **Bounded by construction.** Every command declares a bound (`degrees`, `ms` or `instant`) with a max. The server checks a call's arguments against the tool's input schema; the runtime clamps args to the robot's limits and to the command's schema (§3), chunks what exceeds one operation, then validates what it will really send against the command's full schema. `command_device` and `drive` therefore clamp alike, on a direct call and inside a program. Clamping is reported, never hidden: `clamped: true` and `clamps: [{arg, requested, applied, target}]`, one entry per argument the runtime cut. The `reason` says whether the request was done. A cut target (a distance, an angle, a parameter of the command's bound) that was then reached ends with reason `clamped`: less was done than asked. A cut that is not the target (a speed, a power) leaves the reason `completed`: all that was asked was done, more gently. A device that cuts a value of its own (a tone's frequency) reports `clamped: true` the same way, with what it applied in `measured`.
3. **Explicit state machines** (§1). Illegal transitions return `illegal_state` naming the current state.
4. **Every result carries robot state and `next`.** Errors are typed (§7), never disguised as data.
5. **Nothing is stored between calls, with one exception.** `request_id` is an optional label. A moving call sent twice moves twice: after a failed or unanswered moving call, read the robot (`read_all`) before moving again. The exception is the robot's loop (§5a): while it runs it is part of the robot's activity, and the report of the robot's latest loop is kept until the next loop starts or the link closes.
6. **Fail loud.** Missing reply, stale image, unknown device → typed error. A robot that cannot be configured ends the process at start with a message.
7. **Fast loops live next to the hardware.** Three rates, three places. Conditions and programs run in the server's process (§4): no model turn per check. A loop (§5a) runs where its devices' provider says: on the device itself when the provider has an executor there, else in the server's process at the rate the link carries. The model supervises a loop; it is never inside one.
8. **Safety, honestly stated.** `stop` preempts everything. When the client goes away or the process is signalled, the process stops every robot before it exits (§6). If the process dies outright, the guarantee depends on the driver: stock EV3 firmware has no watchdog, so every motion operation is limited by **time on the brick** (≤ 250 ms, time-based opcodes, never degree-based), the robot overruns at most one chunk even against a blocked wheel, and the bridge page brakes every motor when its socket closes. An ev3dev brick's motors are run by its kernel, which ends a timed run by itself but has no time limit for a move to a position: there the limits are the bridge's (it brakes at the operation's time bound, and after 1 s of silence from the computer) and, when the bridge process itself is killed, a guard process on the brick that brakes every motor as soon as the bridge is gone. The two watch each other: a bridge whose guard is gone brakes every motor and ends, which closes the link, and the link that is opened next starts a bridge with a guard (§1), so no robot is driven without one. While a motor runs on unregulated power (`power` and a loop's outputs, the kernel's run-direct, which has no time limit of its own) the guard is also a deadman: the bridge feeds it on every pass of its scheduler, and a guard that hears nothing for 200 ms brakes every motor, so a bridge that is stopped or hangs mid-loop leaves a motor running for about that long (within 300 ms, tested against a fake sysfs tree). A bridge that hangs during any other move, or a brick whose kernel fails, is covered by nothing. A page device never moves the robot: a manifest that declares `moves: true` is refused (§2.4), so `stop` and the stop at exit are verified whether or not a page answers. A provider whose device has such a watchdog may declare a longer per-operation time bound; the runtime chunks to each command's declared bound, using short chunks only while an `until` condition must be checked; then it reads the condition while every operation runs and aborts the operation the moment it is met, and it also ends every operation itself at ≤ 250 ms of motion by aborting it, so neither a chunk in flight, a slow motor nor a long declared bound delays the reaction. A loop is bounded four ways: its `duration_ms`, its guards (evaluated where the loop runs), the attention window (§5a), and the link watchdog of its provider. Every one of them ends the loop with a brake of every device the loop drives. A loop output is refreshed every tick and each refresh carries a time bound enforced below the loop: on stock firmware the brick ends the motion `hold_ms` after the latest refresh; on ev3dev the kernel ends a refreshed `run_time` at `hold_ms`, and the bridge sets a refreshed power to 0 `hold_ms` after the latest refresh, with the guard's deadman behind it.
9. **Reads have no side effects.** A read never changes a device. Channels needing a sensor mode switch are read only when named explicitly while idle (§2.2).
10. **One owner per rule.** Motion limits: the profile only (`profile.limits` for every robot, `profile.drivetrain` for the distance and the angle of a drivetrain move). Chunking: the runtime only. Program, condition and loop validation: `packages/protocol/validate.ts` only. The law of a loop: `packages/protocol/loop.ts` only (§5a). A loop's ticks, duration and guards: its executor only (§5a). A loop's report: the runtime only. The attention window, the backstop behind a loop and the `looping` activity: `apps/local` only. JSON Schema validation: `packages/protocol/schema.ts` only. Time limits of a call: the runtime only; the process's backstop stands behind them (§1). Link and activity of a robot: `apps/local` only. The check of a page's manifest: `validatePageManifest` in `validate.ts` only.
11. **A person lends, and can take back.** A camera, a microphone or a motion sensor of a page exists as a device only after the person at that page has allowed it there, the page shows when it is in use, and the person can pause or remove it at any moment (§2.4, Privacy). The server keeps no frame, no audio and no transcript: each goes to the MCP client in the result of the call that asked for it, and nowhere else.

## 1. State machines

Per robot, two machines. Their transition tables are exported from `types.ts` (`LINK_TRANSITIONS`, `ACTIVITY_TRANSITIONS`); `apps/local` owns both and asserts every transition against them. A third machine runs per peripheral page (Page, below).

- **Link** `offline → handshaking → online → offline`. `handshaking` = the first device scan plus a verified stop, tried up to 3 times when a stop is not verified within its bound (a bridge that has just started on a busy EV3 can miss the first ones); a robot none of whose 3 stops is verified there comes online in `fault`, and a verified stop there clears an earlier `fault`: a robot that was in `fault` when its link closed is `idle` once a new link has attached, without `reset_fault`. `online → offline` when the robot's link closes: for an `ev3` robot the bridge page, the cable or the brick goes; for an `ev3dev` robot the ssh process ends (the brick, the network or the bridge went away, or the bridge was silent too long). A call in flight then ends with the driver's error, and `list_robots` shows `offline` with `connect`. A twin stays `online`. An `ev3dev` robot comes online by itself, at the start of the process and each time its link has closed: the process opens an ssh link without holding up its other robots, and when an attempt fails it starts the next one 2 s after that attempt ended. A brick that is off or out of reach when the process starts is therefore `offline` with `connect`, and `online` when it answers. With `--install-bridge` an attempt first copies the bridge to the brick, until one copy has succeeded. One attempt takes as long as ssh and the bridge's hello need, at most 60 s (a busy EV3 takes 20 s and more to start Python and the bridge). A link the process closed stays closed: a call still in flight on it answers `robot_offline` at once and opens nothing. An attempt that fails (ssh refused, or a `misconfigured` hello such as a bridge of another version on the brick) writes one `ev3dev_attach_failed` line on stderr, leaves the robot `offline`, and its reason is appended to `connect` in `list_robots` until an attempt succeeds. After a `misconfigured` attempt `connect` says that the robot does not come online by itself: every attempt fails the same way until a person fixes it (a bridge of another version is reinstalled with `--install-bridge` or `"install_bridge": true`; a robot without a `pair` needs bridge version 5, a robot with one runs on version 4 too), and the first attempt after that succeeds.
- **Activity** `idle | acting | running_program | looping | stopping | fault`.
  - One moving call at a time (`drive`, `turn`, `arc`, `run_program`, a `command_device` whose command has `moves: true`): it needs `idle` and takes `acting` or `running_program` before anything is awaited, so of two calls sent together one runs and the other answers `busy` with `retry_after_ms`. Nothing is queued.
  - `stop` is allowed in every state, never waits behind a call, and aborts every call in flight (a move ends with `reason: "preempted"`). `stopping → idle` when every motor reads speed 0 and the preempted call has ended, else `fault`. Stops sent together are one stop. A verified stop in `fault` stays in `fault`. One stop at a time reaches the hardware: a `stop` and a `reset_fault` sent together run one after the other, and `reset_fault` answers with the state the robot ends in (`stop_unverified` when either could not verify).
  - `fault` = a stop could not be verified. It ends with `reset_fault` or with the verified stop of a new link's handshake (Link, above). There, reads, `stop` and `reset_fault` work; `reset_fault` verifies the stop and goes to `idle`, or answers `stop_unverified`. Outside `fault` it answers `illegal_state`.
  - Reads and commands that do not move run in every state (commands: every state but `fault`).
  - `idle → looping` when `run_loop` starts a loop. One loop per robot. `run_loop` plans the loop first: a loop it refuses leaves the robot `idle` and sends nothing. While `looping`, a moving call (`drive`, `turn`, `arc`, `run_program`, `run_loop`, a `command_device` whose command has `moves: true`) answers `busy`; its message names `supervise_loop` and `stop`, and so does its `next`. Reads run. Commands that do not move run, except on a device the loop drives (`busy`). A read that needs a sensor mode switch answers `busy`, as in every state but `idle`.
  - A loop ends by the path of `stop`: `looping → stopping → idle` when every motor reads speed 0, else `fault`. This holds whoever ends it: the `stop` tool, the loop's own duration, a guard, the attention window, an overrun, a lost input, the backstop. A link that closes while the robot is `looping` leaves it `offline` in `fault` (the stop cannot reach the hardware; the brick ends the motion at `hold_ms`), and the next link's verified stop clears it.
  - `ACTIVITY_TRANSITIONS`: `idle: [acting, running_program, looping, stopping, fault]`, `acting: [idle, stopping, fault]`, `running_program: [idle, stopping, fault]`, `looping: [stopping, fault]`, `stopping: [idle, fault]`, `fault: [idle, stopping]`.
- **Cancellation.** When the client cancels a call (`notifications/cancelled`), a moving call is stopped by the same verified `stop` and any other call is aborted; one `{"ev":"cancelled","robot_id","tool","action"}` line goes to stderr. A cancelled `run_loop` or `supervise_loop` stops the robot with the same verified `stop` as a cancelled moving call.
- **Backstop.** A call's own limit is the runtime's (§0.10): `max_command_ms` for moves, `max_program_ms`, `timeout_ms`, `duration_ms`, a blocking command's declared bound. Describes, reads and commands that do not block have none (0). Behind it the process keeps a backstop of that limit + 2 s + `stop_worst_ms`: past it the call is aborted, a moving one is stopped, and the answer is `timeout`; its message says whether the stop was verified, could not be verified, or could not be sent. A read therefore has 2 s + `stop_worst_ms` to answer: one that crosses a slow link to an ev3dev brick and takes longer answers `timeout`. `run_loop`'s own limit is its start window (20 periods, §5a); past it with the margin, the process stops the robot. `supervise_loop`'s is `wait_ms`. Behind the loop itself the process keeps a deadline of `duration_ms` + 2 s + `stop_worst_ms` from the loop's start: past it the process stops the robot and the report's reason is `timeout`.
- A moving call that fails after it started (the link dropped, the backstop passed) answers `retryable: false` with `next` starting at `read_all`: the robot may have moved, so the move is never to be sent again unread.
- **Life** of the process's robots `serving → closing → closed` (§6, Ending).
- **Page** `announced → active ↔ asleep → gone`. One machine per peripheral page (§2.4), owned by `apps/local` (`PAGE_TRANSITIONS` in `types.ts`). `announced`: the page's hello and manifest were accepted. `active`: it answered its first ping; the process pings every 1 s and the page answers from its message handler, with no timer of its own, because a browser fires the timers of a hidden or covered window once per second and delivers socket messages at once (§6, Bridge page). `asleep`: the person pressed "pause", it was silent for 3 s (a locked phone, a frozen tab, a lost network), or its socket closed. `gone`: its socket closed and 30 s passed without the page joining again under the same name. An `asleep` page that answers again and is not paused is `active`; a page that joins again with the token under the name of a page that is not `gone` takes its place at once with the manifest of its new hello, whether or not its old socket was seen to close (§2.4, Joining). A page that is merely hidden or covered stays `active`: on a computer the page is covered whenever the person works in another window. A page is silent while a ping waits for its answer: from its last answer, or from 100 ms before the oldest waiting ping was sent when that is later (in a watch, which pings every 100 ms, from its last answer).
- **A device of an active page can be down by itself.** The page says `{"t":"down","device","why"}` when a device cannot work for the moment (its camera track was muted or ended, the recognizer refuses to start while the page is hidden) and `{"t":"up","device"}` when it can again. A call to a device that is down answers `device_offline` with that reason; the page's other devices work.
- **A page never moves a robot's link.** Link (above) follows the robot's body alone. While a page is `announced` or `asleep`, or one of its devices is down, the devices stay in the registry and every call that needs one answers `device_offline` (§7). When it is `gone` its devices leave the registry (`unknown_device`), and the page is listed as `gone` in `describe_robot` until the process ends.
- While the robot is `offline`, every call answers `robot_offline`, page devices included: a page's devices are part of that robot. A page that must work without a body joins a robot of source `pages` (§6), which has no body and is `online` from the start of the process.
- **Activity.** Every command of a page device has `moves: false`: it runs in every state but `fault`, and it never takes `acting`. One command at a time per page device; a second answers `busy` with `retry_after_ms`.

## 2. Device model

### 2.1 Shape

`DeviceSpec {id, provider, kind, roles[], channels[], commands[], description}` (types.ts). Ids are `<provider>.<local>`: `ev3.A`..`ev3.D` motors, `ev3.S1`..`ev3.S4` sensors, `ev3.pair` synced motor pair (announced only when the robot file declares `pair`, §3), `ev3.speaker`, `ev3.display`, `ev3.led`, `ev3.buttons`, `ev3.battery`; the twin adds `sim.world`, `sim.camera`, `sim.speaker`. Tools accept a device id or a role. A peripheral page's devices are `<page name>.<local>`: a page named `phone` gives `phone.camera`, `phone.mic`, `phone.speaker`. The page name is the provider of those devices, chosen by the person on the page (default `phone` on a touch device, `desk` elsewhere), matching `^[a-z][a-z0-9_-]{0,15}$`, and never `ev3`, `sim` or the name of another page of the robot that is not `gone`. Roles make a mission independent of the page's name. A shipped kind proposes a role in its manifest (`camera` → `eyes`, `microphone` → `ears`, `speaker` → `voice`, `display` → `face`, `touch_panel` → `touch`), and the runtime gives a proposed role to the first device that claims it; a robot file's `roles` wins over a proposal (`"eyes": "phone.camera"`) and resolves while that device is in the registry.

### 2.2 Conventions

Headings, turn angles and rotation rates about the vertical axis are counter-clockwise-positive seen from above (left is positive), in every channel and command: a gyro's `angle_deg` and `rate_deg_s`, an infrared sensor's `beacon_heading`, `turn` and `arc` angles, a pose heading. Motor shaft degrees (`position_deg`, `left_deg`, `right_deg`, the degrees of a motor command) are rotation in the motor's own forward direction, not headings. Channels that share a `mode_group` need a sensor mode switch; only `active` ones are read by default, and a switch happens only when the caller names the channel and the robot is idle. Providers normalize hardware that reports otherwise (the EV3 gyro is clockwise-positive natively, the infrared beacon heading is negative to the left). A channel whose manifest says `null_when_absent: true` may answer that it has nothing to report (the infrared `beacon_heading` and `beacon_distance_pct` with no beacon in view): the reading then has value null and `absent: true`, and that null is an answer. A null without `absent` is a failed read on such a channel as on any other. In a condition every comparison on an absent reading is false (and `changed` sees it come and go), so `turn until beacon_distance_pct < 100` turns until the beacon is seen; it never answers `condition_unreadable`. `describe_device` shows the flag. A gyro's `angle_deg` is cumulative since the gyro's last reset (its `reset` command, or a mode switch), not relative to the start of a call: on a robot that has already turned, `until angle_deg lt -45` can be met at once. `turn` measures the change of heading itself; a condition on the angle needs the reset first. A channel may declare `noise`: how far two readings of a scene that did not change can lie apart, in the channel's unit (§4, `changed`). Distances in cm, speeds in percent unless the unit says otherwise. Image channels return `Reading.image`, never a string in `value`.

A channel may declare `pushed: true`: its device reports each change by itself, the server keeps the latest value, and a read is answered from it with the `ts` of that value, at no cost of a round trip. A pushed value is an answer while its page is `active`; before the page has pushed a channel once, its reading has value null and an error that says so. A camera's `frame` is never pushed: one frame is taken when a read asks for one.

Tilt angles of a device are in degrees about its own axes (`pitch_deg`, `roll_deg`), and a compass heading is counter-clockwise-positive from north like every heading of this contract; the page normalizes what its browser reports.

Touch, light, sound, ultrasonic and temperature cover the EV3 sensors and the NXT ones; the description of a device says which sensor it is. `sensor` is what a provider announces for a sensor it can read but has no entry for: the stock firmware reports its type, its modes and, for the current mode, how many values it returns and their unit; ev3dev reports its driver name, `modes`, `mode`, `num_values`, `units` and `commands`. The model reaches every value through `values` and `index` (a loop's signal, §5a); `set_mode` changes what `values` holds, and the device's `values` channel then states the new number of values and unit. `unknown` remains for a device the provider cannot read at all, with the reason in its description.

**Speech is a declared capability, not a tool.** A speaker lists `speak` only when its hardware can say a text (an ev3dev brick with `espeak` and `aplay`; stock EV3 firmware cannot). The model finds it with `describe_device`; a speaker without it answers `unknown_command`. `speak` has `moves: false` and bound `{kind: "ms", max}` where `max` is the longest a phrase may last (15000): it blocks until the speech has ended (`measured.spoken: true`), is cut at `max` (reason `timeout`), or is aborted — `stop` or aborting the call cuts the audio (reason `preempted`). `voice` is an enum of what the hardware offers, `rate_wpm` is words per minute. A command that does not move and declares an `ms` bound may block that long: the runtime waits for the bound instead of `max_command_ms`, and the process's backstop (§1) stands behind that bound. The twin's `sim.speaker` makes no sound and returns at once: it records the text in `last_spoken` (and counts in `spoken_count`) so a test or a program's success condition can check what was said.

**Listening is a declared capability, like speech.** A microphone lists `listen` only where its browser has speech recognition and the person allowed the microphone; `describe_device` says in the device's description where the recognition runs (on the device, or at the browser vendor's service) as far as the page can tell. `listen` waits for one phrase: it ends when the recognizer returns a final result (reason `completed`, `measured: {heard: true, transcript, confidence, match}`), when `max_ms` passes with nothing recognized (reason `timeout`, `heard: false`, `transcript: ""`), or when it is aborted (`preempted`). `expect` is a list of phrases: the page compares the transcript with each, case and accents ignored, as a substring, and `match` is the first that fits, else `""`. `last_transcript` and `last_match` hold the result of the latest `listen` that heard something, so a program tests `last_match eq "…"` with no model turn. A microphone without `listen` still exists when it can report `level_pct`; one that can report neither is not announced.

A page's `speak` offers `lang` and `voice` as enums of what the browser lists on that device when the manifest is built; a device with no voice for a language does not list that language. An `imu` is not a `gyro`: the runtime takes no heading from it.

The runtime reads and commands a device through its manifest alone: a provider that announces a kind outside this table needs no change in the runtime or the tools.

**Loop outputs (`drives`).** A command may declare `drives: {arg, max_hold_ms}`: a loop may refresh this command every tick with a new value of the numeric argument `arg`; a refresh supersedes the one in flight on that device, and the device ends the command's effect by itself when no refresh follows. `max_hold_ms` is the longest the device lets one refresh last (0 for a command with no lasting motion, such as a light). Only commands with `drives` can be loop outputs; `describe_device` shows them. On stock firmware `run_time` and `power` declare it with `max_hold_ms` 250, and a refreshed value that rounds to 0 brakes the motor. The stock `power_pct` channel is what the provider's latest `power` command or refresh applies while it lasts: the firmware does not report it. On ev3dev, from bridge version 7, `run_time` declares it with `max_hold_ms` the operation's time bound and `power` with 200 (the guard's deadman, §0.8); `power_pct` is the duty cycle the bridge last wrote, 0 once the motor is braked. An older bridge lists neither `power` nor `power_pct` nor `drives`.

**Loop inputs.** Any channel of type `number` or `boolean` (false = 0, true = 1) that is `active`, and one component of a numeric `vector` channel (`index`). A loop never switches a sensor mode: a channel that is not active is refused when the loop is planned, with `next` starting at `read_device` (the rule of conditions, §4).

**Device scans.** The runtime scans its providers' devices when the link is attached and again whenever a provider says its list changed (a sensor plugged or unplugged, a sensor mode switch that moved the `active` flags). A scan that fails after one has succeeded changes nothing: every call keeps working on the registry of the last scan that succeeded, `describe_robot` says so in `scan_error` (why the scan failed and how many times in a row; null when the registry is current), and the runtime scans again by itself after 250 ms, doubling the wait after each failure up to 5 s, until a scan succeeds or the link closes. The first scan of a link has no registry to fall back on: when it fails, the robot does not come online (§1).

### 2.4 Peripheral pages

A peripheral page is a browser page that lends devices to one robot of the process. The process serves the page, the page connects back over one WebSocket, declares its devices, and answers reads and commands. The person at the page decides what is lent. The process holds a page's devices in the robot's *page hub* (`PageHub`, `packages/page-hub`), a provider that is the last of every robot's providers while pages are enabled (§6) and outlives the robot's runtimes: a stock EV3 whose page opens the brick again finds the page devices where they were.

**Joining.** The page opens its socket and sends, as its first message, `{"t":"hello","v":1,"token","robot","name","devices":[…],"unavailable":[{"kind","why"}]}`. `token` is the pairing token of the process (§6). `robot` is a robot id of the process, or absent when the process has one robot. The process answers `{"t":"welcome","name","robot"}`, once the page's devices are in the robot's registry, or closes the socket with a code and a reason the page shows: 4001 bad or missing token, 4004 unknown robot, 4010 the manifest was refused (the reason names the device and the rule), 4029 too many pages (at most 8 per process) or too many wrong tokens from that address (§6). A socket that sent no valid hello within 3 s is closed with 4000. A hello with the token, under the name of a page of that robot that is not `gone`, is that page joining again: the token says it is the same person. It takes the page's place at once, with its devices under the same ids, whether or not the old socket was seen to close (a phone drops a socket without a close frame), and the old socket, if the process still holds it, is closed with 4008, which a page does not retry. The token is checked first: a hello with a wrong token displaces nothing.

**Manifest.** `devices` are `DeviceSpec`s without `provider`, with ids local to the page (`camera`) and at most 4 proposed `roles` each (same pattern as names); the process prefixes the ids with the page name. The process checks the manifest (`validatePageManifest` in `validate.ts`) and exposes it unchanged otherwise; the check is of shape and bounds, never of meaning:
- at most 16 devices, 24 channels and 12 commands per device; the whole hello at most 64 KiB;
- device, channel and command names match `^[a-z][a-z0-9_]{0,31}$`, and no two devices, no two channels of a device and no two commands of a device share a name; `kind` matches the same pattern and is never `motor_pair`; every `description` is at most 300 characters of printable text;
- every command has `moves: false`, a `params` schema of type object with `additionalProperties: false` that uses only the keywords the server's validator implements (`schema.ts`), and a bound of kind `instant` or `ms` with `max` ≤ 30000;
- at most one `image` channel per device, and it is not `pushed`;
- a `pushed` channel is of type number, boolean or string.

A manifest that fails is refused whole (4010): nothing of it is exposed. A page announces a changed set with `{"t":"devices","devices":[…],"unavailable":[…]}` under the same check (a set that fails closes the socket with 4010); the runtime scans again (§2.3, Device scans). `unavailable` lists what the page tried to offer and could not, with the reason in plain words (`"microphone: the person did not allow it"`, `"vibrator: this browser has no vibration"`); `describe_robot` shows it.

**Only what works is declared.** A page builds its manifest from what the browser has and what the person allowed, at the moment it is sent: a kind whose API is absent, or whose permission was refused, is in `unavailable` and not in `devices`.

**Reads and commands.** The process sends `{"t":"req","id","op":"read","device","channels"}` or `{"t":"req","id","op":"command","device","command","args","deadline_ms"}`, with `device` the page's local id; the page answers `{"t":"res","id","ok":true,"readings"|"result"}` or `{"t":"res","id","ok":false,"error":{"code","message"}}` with a code of §7. `readings` is `{channel: value}`; `result` is `{measured, reason, clamped?}`. An image reading is the `res` (with `image: {channel, mime, bytes, age_ms}`, where `age_ms` is the time from capture to sending on the page's own clock) followed by one binary message of `bytes` bytes. `{"t":"req","id","op":"abort","of"}` ends the command `of` in flight (reason `preempted`); `{"t":"req","id","op":"stop"}` ends every command of the page: speech, listening, vibration, tone and torch. The page pushes `{"t":"state","device","values":{channel: value},"ts"}` for its `pushed` channels from the browser event that changed them (a pointer event, a motion event), never from a timer. The process sends `{"t":"ping","n"}` and the page answers `{"t":"pong","n","visible"}`. A read the page does not answer within 2 s answers `device_offline`, and so does a command it does not answer within its bound + 2 s, unless the runtime's own time limit of that command ends it first (reason `timeout`, §4).

**Limits the process holds, whatever a page declares.** A frame is at most 512 KiB and its longest side at most 1280 px (a larger one is a reading with value null and the error `frame_too_large`); at most 2 frames per second per camera (the third answers `busy`); a message is at most 1 MiB; a page that sends more than 100 messages in one second, or anything that is not of the shapes above, is closed with 4000.

**Stop.** The hub's `stop()` sends `stop` to every page that is not `asleep`, waits at most 300 ms for their answers, and returns `motors_stopped: true` in every case; its `stop_worst_ms` is 350. `stop` therefore silences the robot's voice and ends a `listen`, and a page that sleeps or is slow neither delays the stop of the motors nor makes it unverified.

**Sleep.** A page whose person pressed "pause" says `{"t":"paused","why"}` and is `asleep` at once, until it says `{"t":"resumed"}`; one that does not answer a ping is `asleep` after 3 s (§1). A device whose capture stopped is down by itself (§1), whatever the page's state: a camera or microphone track that is muted or ended, a motion sensor while the page is hidden (a browser sends a hidden page no motion events). A page holds a screen wake lock while it lends, and when it is visible again it asks again for the wake lock and for each camera or microphone track the browser ended meanwhile; a device it gets back is up, one it cannot get back stays down with the reason. A page asks for a permission only in a tap of the person: where the browser took one back (`denied`), the device leaves the manifest for `unavailable` with the reason; where it would prompt for it again (Safari on iOS after a lock), the device is down with "tap the page to resume", and the page's banner offers that tap ("Tap to resume camera and microphone"), in which it asks again. A page whose socket closed after its welcome (a phone locks it, or puts the browser in the background) joins again by itself with the same name and token, after 0.5 s, 1 s, 2 s and then every 5 s, at once when it is visible again, and then after it asked again for its wake lock and tracks; it takes its place (§1). After the welcome it says again what is down and that it is paused, since the process starts its devices afresh. It stops trying, and says why, after a close that a new hello cannot change (1001, 4000, 4001, 4004, 4008, 4010, 4029) and 30 s after the close, when the process has let its place go. A command in flight on a page that falls asleep, or on a device that goes down, ends with `device_offline`; for `speak` the message says the phrase may have been cut. The message of `device_offline` says what the person must do ("bring the page named phone to the front and keep its screen on"), and `retry_after_ms` is 2000.

**Privacy.** See principle 11. A page shows a banner for as long as a camera, a microphone or a motion sensor is lent, flashes it on every frame taken and for the whole of a `listen`, and offers "pause" (the page is `asleep`) and "stop lending" (the camera, the microphone and the motion sensors leave the manifest, and their streams and listeners are closed). The process holds a frame only for the time of the call that returns it. The call log (§6) and the page log lines carry no frame, no transcript and no text to speak.

## 3. Robot profile

`RobotProfile {id, roles, drivetrain?, limits, notes}`. Notes are facts for the model, written by whoever built the robot.

- `limits`: `max_speed_pct`, `max_command_ms`, `max_program_ms`, `max_loop_ms` (the longest life of one loop). They hold for every robot, with or without wheels. Providers write `max_speed_pct` into the `maximum` (and, for a signed argument, the `minimum`) of every speed and power argument of their manifests. The runtime clamps every numeric argument of a command that is not a parameter of its bound to the schema's `maximum` when that is above 0 and to its `minimum` when that is below 0, and reports the cut with `target: false` (§0.2); a value between 0 and a bound that excludes it (a frequency under its minimum) is `invalid_argument`. The runtime knows no argument by name. `drive`, `turn` and `arc` cut their own `speed_pct` to `max_speed_pct`.
- `drivetrain` (optional): `{type: "differential", pair_device, wheel_diameter_cm, axle_track_cm, forward_sign, max_drive_cm, max_turn_deg, heading?: {device, channel}}`. `max_drive_cm` and `max_turn_deg` are the longest distance and the largest angle of one `drive`, `turn` or `arc`. `heading` names the channel that measures rotation about the vertical axis in degrees (§2.2); `device` is a device id (`<provider>.<local>`) or a role of `profile.roles`; a robot file whose `heading.device` is neither is refused when it is read. Without `heading`, `drive`, `turn` and `arc` measure the heading from the wheel encoders. The runtime never picks a heading device by kind or by role. A declared heading is never skipped in silence. Devices come and go while a robot is online (a sensor unplugged, another one on its port), so a heading that cannot be used does not end the start; it shows in two places. `describe_robot` has `heading_error`: null when the drivetrain names no heading or the named channel can be used, else a sentence that says why not (the device is not attached, it has no numeric channel of that name, the channel is not active because its sensor is in another mode). And a move that names a heading and could not measure with it (one of those reasons, or a read of the channel that gave no number at the start or at the end of the move) measures the heading from the wheel encoders and says so twice: `measured.source` is `encoders`, and `measured.heading_error` holds the reason. `measured.source` is `gyro` when the heading channel measured the move, and `measured` then has no `heading_error`. A robot whose drivetrain names no heading answers `source: "encoders"` with no `heading_error`.
- A robot file's `hardware` may name `ir_channel` (1 to 4, the channel switch of the infrared remote): every infrared sensor of the robot reads its beacon and remote on that channel. Without it, channel 1. A value outside 1 to 4 is refused when the file is read.
- A robot file is `{hardware, profile, pair?, twin?, description?, name?}`; any other top-level key is refused when it is read, naming the key. `pair` (`{left, right}` motor ports) exists only for a robot whose two motors are driven as one synchronized device; the provider announces `<id>.pair` only then, and without it those two ports are two `motor` devices. A `drivetrain` needs the `pair` its `pair_device` names: a robot file with a `drivetrain` and no `pair` is refused when it is read.
- `name` (optional) is what the person calls the robot ("Rayo", "Doña Tuerca"), apart from `profile.id`, which stays the robot id of every tool call. It is trimmed and put in NFC, then holds 1 to 22 characters (one line of the EV3's screen), each a letter (any script, accents too), a digit, a space, `'`, `.` or `-`; anything else (empty, longer, a control character, a line break, a quote) is refused when the file is read, naming `name`. `--name <text>` gives every robot of a command line that name, over its file's, by the same rule. A robot and its twin, read from the same file, share it. It is the person's and the model's, not the runtime's: `list_robots` and `describe_robot` give it as `name` (null without one), with the rule `ROBOT_NAME_RULE` of `tools.ts` on how to use it, which `SERVER_INSTRUCTIONS` carries too; the 3D page shows it as the robot's title; and a named robot whose devices include `ev3.display` writes its name on that screen once it is online (a screen that refuses, as in `fault`, is logged as `greet_failed` and changes nothing else). Without a name, nothing of this happens.
- `twin` (optional) is the robot's build as its twin needs it: how the person put this robot together, so that its twin is that robot in any world. `{body?, ev3?, view?, drive?, unconfirmed?}`; `body`, `ev3` and `view` each the shape of the world-file section of the same name (`body`: the footprint and where the colour and distance sensors sit, from the centre of the wheel axle; `ev3`: what is plugged into each port, `{motors: {A..D: "large" | "medium"}, sensors: {"1".."4": "touch" | "color" | "ultrasonic" | "gyro" | "ir"}}`; `view`: how it looks in 3D, the schema in the header of `apps/twin-view/src/look.ts`). A file with `twin` owns its whole build: the twin takes `body`, `extensions.ev3` and `extensions.view` from it, and a section it leaves out takes the package default (the default body, an empty port map, the default look), never the world's. A file without `twin` takes those three sections from its world, as before. The rest of the world (arena, boxes, zones, lines, points, start, noise, its other extensions) is the room's. Only a twin reads `twin`: a robot on hardware reports what is plugged into it (`describe_robot`). It is checked whenever the file is read, every field named as `twin.<field>`; `view` must be an object and is otherwise read by the 3D page, which keeps a default for a field it cannot use. `twin.drive` (optional, needs `profile.drivetrain`) is the drivetrain as the robot physically is, `{wheel_diameter_cm?, axle_track_cm?, turn_scrub?, mass_g?, grip?}`: the wheel that really rolls, the track the body really turns on, the share of a turn a skid-steer base loses to its treads scrubbing sideways (0 up to, not including, 1; 0 when absent; an estimate until it is measured on the robot: `turn 360` with the heading from the wheel encoders, the angle the body really turned read off a line on the floor or a protractor, `turn_scrub = 1 - true/360`; list `drive` in `twin.unconfirmed` until then), and what the robot weighs with the friction coefficient of its tread on the floor (both or neither; §4 Twin, pushing). An absent length is the profile's. The twin's brick and physics run on these while the runtime plans every move with the profile's `drivetrain`, as it does on the robot; so a profile that is wrong makes the twin miss as the robot misses, and correcting the profile (`turn` 360, measure, scale `axle_track_cm` by 360 over what it turned) corrects the twin. The scrub is the robot's, not the room's: a world file's `noise.turn_scrub` is refused, naming `twin.drive.turn_scrub`. `--doctor` prints a physical length where it differs from the profile's (`axle track 16 cm (really 13.5 cm)`).
- `twin.unconfirmed` (optional) lists what of the build nobody confirmed (no brick report, no person, no legible photo): a twin built from it is a draft, and a list that is absent or `[]` means every value was confirmed. Each entry is one of a closed set, at most once: a port `A`..`D`, `S1`..`S4` (what is plugged in there and its role; allowed whatever `twin.ev3` says of that port, since an unseen port may not be empty), `left_right` (which `pair` port drives the left side; needs `pair`), `front` (which end is the front: `forward_sign`, `front_cm` against `back_cm`, the sign of every `x`), `drive` (wheels, tracks, or no drive), `wheel_diameter` and `axle_track` (need `drivetrain`); these change how the robot moves. `footprint` (the `twin.body` lengths) and `places` (where the brick, the sensors and the phone sit) change only what the twin collides with and how it looks. Any other entry, a repeat, or a drive entry without its `pair` or `drivetrain` is refused when the file is read, naming `twin.unconfirmed`. The twin runs as any twin; `--doctor` prints the list in a `warn` line `draft <twin id>`, and the 3D page receives it as `extensions.view.unconfirmed` (the list as written; present only when it is not empty), so `twin.view.unconfirmed` itself is refused.
- The ports of a twin and its profile agree, or the start ends naming the field and both ways to fix it: a role (or `drivetrain.heading.device`) naming `ev3.A`..`ev3.D` needs a motor on that port, one naming `ev3.S1`..`ev3.S4` a sensor on that port, one naming `ev3.pair` a `pair`; both ports of `pair` need a motor; a `drivetrain.pair_device` of the form `ev3.<x>` must be `ev3.pair`. Other device ids (`sim.*`, a page's) are not checked. `--doctor` with `--twin` prints, per twin, what it will have (its ports, pair and drivetrain numbers, footprint, and where its build came from), or this error. `--doctor --files-only` prints only those lines (`robots`, `twin <id>`, `draft <id>`) and checks nothing of the computer: its exit code is 1 only when a robot file is refused.
- A robot without `pair` and without `drivetrain` is complete: its motors and sensors are devices, `drive`, `turn` and `arc` answer `unsupported` with `next` starting at `describe_robot` and `command_device`, and everything else works. `describe_robot` shows `drivetrain: null`, and the `next` of a result on such a robot names `command_device` where it names `drive`, `turn` or `arc` on a robot with wheels. Its twin's motors turn and its body stays where the world put it.
- A robot of source `pages` (§6) has a profile and no hardware: its file is `{profile: {id, roles, limits, notes}, description?, name?}`, with no `pair` and no `drivetrain`. It is a complete robot with zero devices of its own; every device it has is lent by a page. Its `backend` is `page`.
- The example robots are `deployments/example/robots/r1.json` (a two-wheel base: pair B+C, wheel 5.6 cm, axle 12 cm, heading from its gyro), `deployments/example/robots/arm.json` (two free motors and a sensor, no pair, no drivetrain) and `deployments/example/robots/pages.json` (no body: the devices of the pages that join it).

## 4. Runtime

Owns chunking: it splits every motion into operations no longer than the command's declared time bound (short ~200 ms chunks only when an `until` must be evaluated), coasting between chunks with `brake:false` only when the link's round trip is small next to the chunk time (otherwise every chunk brakes) and braking on the last. The round trip that decides is the slow end of what was measured: the larger of the provider's latest timed reading and the 90th percentile of its latest 10, and it must be under a quarter of the chunk time. A link timed fewer than 3 times never coasts; the runtime times a new link up to 3 times with nothing moving, stopping at the first answer that is too slow to coast. One fast answer on a slow link therefore never coasts, a link that turns slow stops coasting at its first slow answer, and after slow answers coasting returns when the latest is fast and they are at most one in ten. Under `until` the runtime watches the condition for the whole move: it reads the condition's devices every max(10 ms, the round trip of one such read), also while an operation runs, and aborts the operation in flight the moment the condition is met, so the reaction time is one poll plus the abort's way to the device, not the rest of a chunk. A channel's `max_rate_hz` does not slow the watch down. A poll in which a channel of the condition returned no value decides nothing: the condition is not met for that poll, whatever its combinators (`not` included), and the watch polls again. Three such polls in a row on the same comparison (about 30 ms of a watched move, inside one chunk) end the watch: one lost exchange with a brick is not a broken sensor, a sensor that stays silent is. The watch then ends the move like a met condition does (the operation in flight aborted, the device braked), one reading with nothing running measures what was done, and the call answers `condition_unreadable` with `error.measured` (§7); the message names the channel, the number of polls and the reading's error. A move whose condition cannot be read when the call starts sends nothing. Any other error of the watch (the sensor's device left the registry after it was unplugged, the link closed) ends the move the same way under its own code, with `measured` when the wheels can still be read. `wait_until` and a program's `while`, `if` and `success` follow the same rule: a poll without a value is asked again 10 ms later, and the third in a row ends them with `condition_unreadable`. A channel declared `null_when_absent` (§2.2) is the exception when its reading says `absent`: that null is an answer. Ten polls in a row that decide nothing, whichever comparison lacked its value (channels failing in turn), end the watch with `condition_unreadable` too. `wait_until` ends at `timeout_ms` whatever its polls return, and a call aborted while its watch waits for an answer ends at once. After an operation that braked, the next one is sent only after a reading taken since; after one that coasts it is sent at once, watched. It also gives every operation a deadline of ≤ 250 ms from the moment it is sent and aborts the operation there (the abort travels the same link as the request, so the device has moved for that long when it lands): that abort is a chunk end, not a preemption, and the provider answers it like any abort (motion ended, `measured` so far). `max_command_ms` bounds a chunked move (`drive`, `turn`, `arc`, a `command_device` bounded in degrees or ms) while its operations run: a time target is never sized past what the budget still holds, and an operation still running when the budget is spent is aborted at that moment, so such a move outlives `max_command_ms` by the abort's way to the device and the closing reading. It ends with reason `timeout`. A command sent as one operation (an absolute target such as `run_to_position`) is aborted 250 ms after `max_command_ms`: a device that ends at its own time bound answers by itself first.

Measuring a move costs no round trip of its own. The reading of the wheels (and of the drivetrain's heading channel, when the profile names one) a move starts from is sent together with its first operation, and every later operation carries one too: **a provider serves calls in the order they were made**, so a reading made right before a command shows the device before that command starts. Progress is that reading plus the operation's own `measured`; what the device moves by itself between two operations (coasting on, creeping after a brake) shows in the next reading and is expected when the following operation is sized. A move ends `stalled` from what the device did, never from how slow the link or the host is: three operations in a row that each moved less than a tenth of their step, or the device's own `stalled`; an operation that ended at a time bound (the runtime's cut, or the device's: reason `timeout` with `measured.time_limited`) was never going to cover its step, and there the motion that adds up over such operations is progress, so a long move on a link too slow to coast (every operation braked, each sent the whole remainder) does not stall on a clear floor. One reading with nothing running closes the move, decides whether the target was reached, and is what `measured` reports. Those readings also time the link. Coasting needs a round trip timed just now: in the same call before anything moves, or at most 500 ms ago (moves sent back to back, as a program or a script does; that is how old the evidence gets between two chunks of one move). An older one is not evidence, the link may have changed: then, on a link last seen fast, the first reading is awaited. On a link last seen too slow to coast nothing is awaited, every operation brakes, and the readings show it when the link is fast again. Providers execute exactly one time-bounded operation per call. Runs in the server's process (§6). It hosts providers (`Provider` in types.ts): the EV3 provider, the ev3dev provider, the sim providers. It implements every `RobotTool` (types.ts) with the semantics in `tools.ts`, executing `until` by watching the condition while ≤ 250 ms chunks run, and programs node by node. Errors are `RuntimeError{code}` from the §7 set.

**Operations and ticks.** `Provider.command` executes exactly one time-bounded operation and resolves when it has ended; a device that runs one refuses a second (`busy`). `Provider.loop` is the other way, and only a loop uses it. A provider that has it declares one of two shapes (`ProviderLoop` in types.ts):

```ts
type ProviderLoop =
  | { runs_on: "host"; max_rate_hz: number;
      // One exchange with the hardware: refreshes every output, then reads every input, in that order.
      // A refresh supersedes the refresh in flight on its device and is bounded on the device at hold_ms.
      tick(writes: {device: string; command: string; args: Record<string, Value>}[],
           reads: {device: string; channel: string; index?: number}[],
           hold_ms: number): Promise<(number | null)[]>;
      // Brakes the driven devices and releases them.
      end(devices: string[]): Promise<void> }
  | { runs_on: "device"; max_rate_hz: number;
      // Hands the planned loop to the device, which runs it by itself and pushes telemetry and its end.
      start(plan: LoopPlan, on: (ev: LoopEvent) => void): Promise<{
        set(params: Record<string, number>, ramp_ms: number): Promise<void>;
        end(): Promise<void>;                 // brakes; `ended` then resolves with reason preempted
        ended: Promise<LoopEnd> }> };
```

A device that a loop drives is claimed for the life of the loop: `command` on it answers `busy`. The 250 ms rule of §0.8 holds for ticks through `hold_ms`. The runtime's host executor is one timer on the runtime's clock, with absolute deadlines (tick n is due at start + n × period), calling `tick` once per period and `packages/protocol/loop.ts` between two ticks; a tick refreshes each output with what the law computed on the previous tick. A stock provider's tick is one direct command, and a stop overtakes a tick still waiting in the queue: that tick goes out without its refreshes.

**Page devices.** A page device is read and commanded through the hub like any provider's device. A condition on a `pushed` channel is evaluated from the latest pushed value, so an `until` watch costs no round trip to the page and keeps its 10 ms poll. While a page's pushed channels are being read (a watch reads them at every poll), the process pings that page every 100 ms, and a pushed value is a poll without a value once its page is silent for 300 ms (the rule above): three in a row end the watch with `condition_unreadable`, whose message carries the `device_offline` reason. A move guarded by a page's channel is therefore braked about 330 ms after its page falls silent, and a paused page or a device that is down ends it at the next poll with `device_offline`. In a loop a page device is an input only (§5a): a tick reads a pushed channel's latest value by the same rule, and while a loop reads a page the process pings it every 100 ms until the loop ends, whatever the loop's rate.

**Conditions are checked before anything is sent.** A condition (`until`, `wait_until`, a program's `while`, `if` and `success`, and the `until` of every call in a program) is compiled against the devices when the call is planned. Two things fail there with `invalid_argument`, and the robot has not moved:

- A comparison on a channel that is not active (its sensor is in another mode of its `mode_group`): a condition never switches a sensor mode. The message says that nothing was sent and names the channel and the active ones, and `next` starts with `read_device`, which switches the mode when it names the channel (§7). When the registry said active and the device answers otherwise at the first poll, the call fails the same way and sends nothing.
- A comparison that the channel's declared `range` can never make true: `lt` at or under the low end, `lte` under it, `gt` at or over the high end, `gte` over it, `eq` outside it. `distance_cm lt 2` on a channel of range [3, 255] is refused, and the message names the range. The comparison is refused wherever it stands in the condition, also under `not`, where it would always hold.

**The smallest move of a drivetrain.** Wheel encoders count whole degrees, so the smallest target of `drive`, `turn` and `arc` is the one that turns the leading wheel by 1 degree: 0.05 cm and 0.47 degrees for the example base (§3). A nonzero target under it, of either sign, is answered as done: nothing is sent, the result is `ok` with reason `completed`, the target in `applied` is 0, `measured` is what the wheels read (about 0), and `note` is one sentence that names the minimum in the tool's own unit. A script that computes a correction (`turn(90 - measured)`) therefore goes on when the correction is too small to make. The call is still planned like any move: its `until` is compiled, and the robot must be online and idle. A program step answers the same way and carries the `note`. A target of exactly 0 is no motion and answers `completed` with nothing sent and no `note`. A move just over the minimum overshoots by a few wheel degrees; `measured` says by how much.

**`changed`.** The comparison holds when the channel's value differs from the first value the call read. On a channel that declares `noise` (a number, or each component of a numeric vector) the difference must be larger than the noise in 2 polls in a row, so a still sensor does not meet it and one outlier does not either; that costs one poll (10 ms in a watched move). On a channel without `noise` (booleans, strings, counters, encoders) every difference is a change, at the first poll that shows it.

Twin: `<profile.id>-sim` is a runtime whose EV3 provider talks to a **simulated brick** (byte-level EV3 direct-command emulator backed by 2D physics), so the twin runs exactly the real EV3 code path. Its motors and sensors, its footprint and its look are its robot file's `twin` (§3), else its world file's. A world that `load_world` takes, by name or as a whole JSON string, gets the robot file's build the same way, so the robot keeps its ports, footprint and look in every room. **What happened.** The world keeps a log of its last 200 events in simulated time, and `sim.world events{since?}` returns those after number `since` (default 0), oldest first: `measured.events` holds each as a JSON object in a string, `{n, t_ms, kind, ...}`, with `measured.next` (the `since` of the next call), `measured.dropped` (events after `since` no longer kept) and `measured.t_ms` (the world's time now). The kinds: `contact_began` / `contact_ended` `{with}` (a box's id, or `wall_west` (x 0), `wall_east`, `wall_south` (y 0), `wall_north`; within 0.01 cm counts as touching), `push_began` `{box}` / `push_ended` `{box, moved_cm}`, `stall_began` / `stall_ended` (a drive wheel held, its encoder stopped), `slip_began` / `slip_ended` (the drive wheels turn while the body is held), `echo_lost` `{why: "slant" | "range"}` / `echo_back` `{cm}` (only with an ultrasonic sensor plugged in; `slant`: a surface in range met too far off square to echo, `range`: nothing within 250 cm), `placed` `{how: "reset" | "carried"}` and `obstacle_changed` `{box, change: "added" | "moved" | "removed"}` (a person's hand). A contact is timed where it happened within its physics step (to 2^-12 of the step), so a watching page does not move it; the other events are stamped at the end of the step they happen in (at most 20 ms later, and where a watching page cuts the steps). Recording and reading the log spends no noise and changes nothing the robot does or reads. Every obstacle of a world has an `id` for as long as it exists: the world file's (`obstacles[i].id`, 1 to 32 letters, digits, `_` or `-`, unique), else the next free `box<n>`; a box set down later gets a `box<n>` no box of that world has had. A person's changes go through the world by id (`addObstacle`, `moveObstacle`, which keeps a box's id and place in the list, `removeObstacle`, `setObstacles`), each refused whole with a code (`invalid`, `outside`, `on_robot`, `no_such_box`, `id_taken`), and every change of the obstacles, a person's or a push's, counts in `obstacles_rev`, so a viewer knows when to show them again. It adds three devices that no hardware robot has: `sim.world`, `sim.camera` and `sim.speaker` (the only speaker of a twin with `speak`).

The twin's physics keep the surprises of the real robot, so that what works on the twin works on the floor. A body that drives into a wall or an obstacle stops in contact with it, and its drive wheels stop there: their encoders count up to that point and no further, and the move ends `stalled`. Motors: a shaft follows a power command as a first-order lag of 76 ms (`MOTOR_TAU_MS`, measured on EV3 large motors without regulation), so it is at 90 % of a new speed after 175 ms. A speed command (the stock provider's moves, the SPEED and SYNC opcodes) is regulated: the firmware's speed loop drives full power until the shaft reaches the setpoint and holds it there, so a start to 50 % reaches its speed after 53 ms (ev3dev's log, its own regulator: 47° of `run_degrees @20` and 59–60° of `run_pair @25` in the first 250 ms, about 90 % of the full-speed distance; no stock-firmware trace found). The speed a motor reports is the speed it turns at. The medium motor has its own constant, `MEDIUM_MOTOR_TAU_MS`, 76 ms too until it is measured (no measurement found), and its own speed, 1560 °/s at 100 %; the stock EV3 provider sizes moves and reports `speed_deg_s` for each motor at its own type's scale (on a robot 1050 °/s per 100 % for a large motor and 1560 for a medium one, ev3dev's `max_speed`; on a twin the simulated motors' 1020 and 1560), so a medium motor's speed is not read a third too low. A command that ends with brake stops the shaft where the brake came (the firmware holds it there; the tens of ms of overshoot and return are not modelled); one that ends without brake runs down under friction alone, for 1.4 s and about 710° from 100 % (a quarter of the distance from 50 %; `COAST_MS_AT_100`, an estimate from the motor's no-load current and shaft inertia, 1.1–1.7 s, not a measurement; a wheel under a robot is not measured either); a new command picks the shaft up at the speed it has. A degree-bounded step (never sent by the stock provider) ends exactly on its count. A robot's `twin.drive.turn_scrub` (§3; 0 by default; an estimate unless measured as §3 says) makes a skid-steer base turn `1 - turn_scrub` of what its encoders say, as tracks that scrub sideways do; straight travel is untouched and the encoders report what the motors turned, so a turn measured by encoders falls short and one measured by a gyro does not. Obstacles may be low and may be pushed. An obstacle's `height_cm` (absent: taller than anything) decides what sees it: a distance sensor mounted `body.distance_sensor_z_cm` up (default 6) sees a box only where its beam, spreading up and down by its half angle as it does sideways, comes down to the box's top, so mounted at 20 cm it looks over a 10 cm box until about 47 cm away, and the top edge it then meets echoes from a little farther and more slanted. The touch sensor's bumper feels what is within 0.7 cm ahead of the front across the body's width and at least as tall as `body.touch_z_cm` (default 0); a wall along the robot's side does not press it. The body is stopped by a box of any height. An obstacle with `mass_g` slides when the robot pushes harder than its floor friction, 0.4 × its weight (`BOX_FLOOR_FRICTION`; no measurement of cardboard on a classroom floor found, wood on wood is 0.25–0.5): it moves the least way that clears the body, stays against it, never turns (an off-centre push slides it straight), carries no speed of its own (a light box stops at once), and stops against a wall or a box it did not already overlap, and the robot stops behind it. The most the robot pushes is the traction of its tread, `grip × mass_g × g` from `twin.drive`, and never more than its two motors turn against (2 × stall torque / wheel radius; stall torque 40 N·cm large, 12 N·cm medium, as LEGO states); a build that does not say what it weighs pushes 4.9 N (`DEFAULT_PUSH_N`: 1 kg at grip 0.5, between the 0.25 of plastic EV3 track links and the 1.0–1.2 of LEGO rubber tyres measured on wood). A heavier box is a wall. The load slows the drive along each motor's torque-speed line: a regulated motor reaches at most `(1 − load torque / stall torque)` of its full speed, so pushing a 1 kg box (3.9 N) on 5.6 cm wheels costs a large motor about 14 % of full speed and nothing at half speed. A build with `mass_g` and `grip` whose traction is below what its motors turn against slips at a wall: its wheels keep turning near the speed they were given and the body stays, so a move ends on its count, not `stalled` (plastic tracks at 0.25 do this). A build without them stalls there, as above. Pushing, like driving, does not depend on how a watching page cuts the physics steps: a straight push lands the box and the robot within 0.05 mm whatever the steps; a turning push is resolved step by step and may differ by more. An infrared sensor's `proximity_pct` is the light its beam (±25°) gets back: a large wall square on reads about 1.07 % per cm (41 at 38 cm, as the stock firmware reads a white wall), a wall at a slant, an object narrower than the beam or a darker one reads farther (an obstacle's `ir_reflectivity`, relative to white, absent 1; black about 0.21 reads 89 at 38 cm, as the stock firmware does, and is out of range from about 56 cm), 100 means nothing within about 94 cm for a white wall (linear from the measured point; LEGO and ev3dev say about 70 cm, and the sources cannot both hold with the black-wall measurement, so the twin keeps the measurements), and its noise grows with the reading (`noise.ir_pct` at 40 %). An ultrasonic sensor's `distance_cm` is the nearest echo anywhere across its ±12° cone (searched along every bearing where one can come from, so a thin post far away does not hide between rays); a hard surface echoes only where the cone meets it within 13° of square, so a wall slanted more than about 25° off the sensor's axis gives no echo and the sensor reads 255, as it does with nothing within 250 cm. A box's corner (a convex edge) scatters sound back at any angle: one inside the cone and in plain view, within 60 cm (`ULTRASONIC_EDGE_MAX_CM`, not measured: kept short so that a strategy that relies on seeing an edge sees it on the robot), echoes at its distance; so does a corner of the room (two walls square to each other send the sound back the way it came), within the same 60 cm (`ULTRASONIC_CORNER_MAX_CM`, not measured either); where a box meets a wall the faces' rule alone decides. A gyro's `rate_deg_s` saturates at ±440 °/s as the sensor's specification says (`GYRO_MAX_DEG_S`; a spin at 100 % on 5.6 cm wheels 12 cm apart turns at 476); the angle it would then lose is not modelled. A gyro counts each real degree as `1 + e` degrees, `e` drawn from the seed (`noise.gyro_scale`, about ±3° on a 90° turn as LEGO states), and a gyro reset (a mode switch, `gyro.reset`) while the robot turns takes that rate as its zero, so its angle drifts by it until a reset while still.

## 5. Programs

JSON tree (`ProgramNode` in types.ts), no code. Caps: 500 nodes, `repeat.times ≤ 50`, `while.max_iterations ≤ 200`, `wait_ms ≤ 10000`, total ≤ `limits.max_program_ms`. `run_program` takes the program inline (`body`, optional `success` condition checked at the end). The runtime validates it (`validate.ts`), executes it node by node and returns per-step results: `steps: [{path, tool, ok, reason | error, measured?, clamped?, note?, ms}]`, one per call the program made (and per `wait_ms`). A step carries the `reason` and the `measured` of the same call made outside a program, and `clamped: true` when that call cut an argument, so the result says what each step did without a read after it. A step that failed has `error: {code, message}` and, when the error ended a move, the `measured` of that move.

## 5a. Loops

A loop is a control law that runs at a fixed rate next to the hardware: every tick it reads its input signals, computes each output, and refreshes each output device. It is given as data, like a program, and is bounded by construction. This section is the law and its data: `LoopSpec` and the types beside it in types.ts, `validateLoop` in `validate.ts`, and `planLoop`, `stepLoop` and `setParams` in `packages/protocol/loop.ts`, which are pure (no I/O, no clock). No use is named anywhere in it: balancing, following a line or a wall, and holding an arm at an angle are each one `LoopSpec` (`docs/loops.md`).

**Shape** (`LoopSpec` in types.ts):

```
{
  rate_hz,                       // ticks per second
  duration_ms,                   // the loop ends by itself at this age; cut to the robot's limit on a loop's life (reported)
  attention_ms?,                 // default 15000: how long a loop may run unsupervised
  signals: { <name>: { device, channel, index?, zero?, detrend_s?, smooth_ms? } },
  params?: { <name>: number },   // named numbers the law refers to; the only thing that changes while a loop runs
  outputs: [ { device, command, args?, terms: [Term, ...], limit?: [lo, hi] } ],
  guards?: [ { name, signal, of?, op, value, for_ms? } ],
  trace_hz?                      // default 10, at most 20
}
Term = { signal, of?, setpoint?, gain, clamp? }  // feedback on one part of one signal; of: value (default) | integral | derivative
     | { feed, gain? }                          // feedforward: gain × the value of param `feed`; gain defaults to 1
```

A `setpoint`, a `gain` and a `feed` are each a number or the name of a param. Caps: 8 signals, 4 outputs, 16 terms per output, 8 guards, 16 params.

**Loop inputs and outputs.** A signal reads a channel of type `number` or `boolean` (false = 0, true = 1), or one component of a numeric `vector` channel (`index`). A loop never switches a sensor mode: a channel that is not `active` is refused when the loop is planned, with `next` starting at `read_device` (the rule of conditions, §4). An output refreshes one command every tick with a new value of one numeric argument. Only a command with `drives: {arg, max_hold_ms}` (`LoopDrives`) can be an output; a plan is handed it per output (Planning, below). `arg` is that argument, and `max_hold_ms` is the longest the device lets one refresh last (0 for a command with no lasting motion). A loop holds each refresh for `hold_ms` = 3 periods, at least 30 ms, at most `max_hold_ms`. `args` holds the command's other arguments, the same on every refresh. 0 is the value an output rests at: every output is 0 while the loop settles and on the tick that ends it, whatever its `limit`, so the range of `arg` must hold 0.

**Ticks.** dt is the measured time between two ticks, in milliseconds; the law reads no clock. The first tick has no dt: on it every derivative is 0 and every integral is 0. A tick with a dt of 0 is a tick: its reading is taken, guards see it, and only the derivative keeps the value it had. A tick whose dt is above 10 periods ends the loop with reason `overrun`: the law never integrates across such a hole. A tick on which a channel returns no value keeps that signal's value and derivative; the next reading's derivative and filters span the whole gap. A reading that is not a finite number, or lies beyond ±1e9, is no value. Three ticks in a row without a value end the loop with reason `input_lost`. On the tick that ends a loop, whatever the reason, every output is 0.

**Magnitudes.** No output can leave the finite numbers, so none that is not a number reaches a device. Every gain, setpoint, feed, param, `clamp` and guard value lies within ±1e6, `detrend_s` and `smooth_ms` are at most 1e6, readings lie within ±1e9, and the law holds every derivative, every signal integral and every term's accumulator within ±1e12.

**Signals.** Each tick a signal has a `value`: the channel's reading after `zero`, `detrend_s` and `smooth_ms`, in that order.
- `zero: "start"` subtracts the first reading the loop takes of the channel (an encoder, a cumulative angle). `zero: {mean_ms}` holds every output at 0 for `mean_ms` from the signal's first reading, subtracts the mean of the readings it took in that time, and ends the loop with reason `not_still` when those readings spread more than 4 × the channel's `noise` (the offset of a rate gyro). Absent: the reading as it is. While any signal measures its mean the law has not started: filters, derivatives, integrals and guards begin on the first tick after, which is the law's first tick.
- `detrend_s` subtracts a running mean with that time constant (slow drift of a rate sensor): each tick the mean moves toward the reading by dt / (`detrend_s` + dt) of their difference. The mean starts at the signal's reading on the law's first tick.
- `smooth_ms` is a first-order low-pass with that time constant: each tick the value moves toward its input by dt / (`smooth_ms` + dt) of their difference. It starts at its input on the law's first tick.
- The derivative of a signal is the change of its `value` over dt.

**Law.** For every output, every tick, `u` is the sum of its terms:

| term | contributes |
|---|---|
| `of: value` | gain × (value − setpoint) |
| `of: derivative` | gain × (d(value)/dt − setpoint); the setpoint is a rate, per second |
| `of: integral` | gain × I, where I is the term's own accumulator: I grows by (value − setpoint) × dt each tick and starts at 0. With `clamp`, I is held within ±`clamp` (in the signal's unit × seconds) |
| `feed` | gain × the param |

A setpoint is 0 when absent. Then `u` is cut to `limit` and to the `minimum` and `maximum` of the command's `drives.arg` in its `params` schema, and the command is refreshed with it. An accumulator is a state of the law like any other: it follows its signal whatever the output does, and only its own `clamp` bounds it. A PID on one signal is three terms on it (value, integral with a `clamp`, derivative). State feedback is one term per state, with the integral and the derivative giving the states a sensor does not report (the angle of a rate gyro, the speed of an encoder). A positive gain raises the output when the signal is above its setpoint: an actuator that raises the signal it is regulated on takes negative gains.

**Params.** `setParams` changes named numbers between two ticks, all of them on the same tick; with `ramp_ms` (at most 3600000) each moves to its new value linearly over that much loop time, from the value it has on that tick, also in the middle of another ramp. A new value lies within ±1e6 and names an existing param, else `invalid_argument`. Integrals and filters keep their state. Signals, terms, guards, limits and the rate are fixed for the life of a loop: a different law is a new loop.

**Guards.** `{name, signal, of: value | integral | derivative (default value), op: gt | lt | abs_gt, value, for_ms?}`. A guard's `integral` is the sum of value × dt since the law's first tick, with no setpoint. A guard that holds on a tick (on every tick of `for_ms` in a row when given) ends the loop on that tick, where the loop runs, with reason `guard` and the guard's `name`; of two guards that hold on the same tick the first of the list gives the name. A guard is how a loop says "fallen", "line lost", "bumper pressed" or "arrived": the caller decides what the name means.

**Validation.** `validateLoop` checks a spec without a robot, and every failure is `invalid_argument` with the path of the field (`loop.outputs[1].terms[0].gain`): the caps above; unknown keys; `rate_hz` of at least 0.1; `duration_ms` and `attention_ms` integers of at least 1; `trace_hz` above 0 and at most 20; at least one signal and one output; names of signals, params and guards made of 1 to 32 letters, digits and `_`, not starting with a digit and never `__proto__`; `device`, `channel` and `command` strings of 1 to 64 characters; a signal never named `t_ms` or `out<i>` (keys of the trace); `index` an integer of at least 0; `zero` either `"start"` or `{mean_ms}` with `mean_ms` an integer from 1 to under `duration_ms`; `detrend_s` and `smooth_ms` above 0 and at most 1e6; no two outputs with the same `device` string; `limit` two numbers with lo ≤ hi; a term either feedback or feed, never both; `clamp` above 0, at most 1e6, and only on a term of integral; a guard's `name` unique, its `op` one of the three, its `value` within ±1e6, its `for_ms` an integer of at least 1; every signal a term or a guard names exists; every `setpoint`, `gain` and `feed` a number within ±1e6 or the name of an existing param; every param within ±1e6.

**Planning.** `planLoop` checks a spec against the robot and returns a `LoopPlan`: every default filled in, signals and outputs in the spec's order, every device by its id, each output with its `hold_ms` and its bounds (`limit` cut to the range of `drives.arg`). What it needs from the robot comes as data (`LoopContext`): per signal the channel's manifest entry and the id of its device, per output the id of its device, the command's `drives` and the range of its argument, `max_rate_hz` and `max_loop_ms`. A context that lacks a device id, or holds a number that is none (a negative `noise` or `max_hold_ms`, a rate of 0), is `misconfigured`. It refuses a spec `validateLoop` refuses, and it refuses, and nothing is slowed, switched or dropped silently:

| refused | code |
|---|---|
| `rate_hz` above `max_rate_hz`, the fastest rate where the loop runs; the message names the maximum | `invalid_argument` |
| a channel that is not `active`; `next` starts with `read_device` | `invalid_argument` |
| a channel of type `string` or `image`; a `vector` channel without `index` or with one outside its length; an `index` on a channel that is no vector | `invalid_argument` |
| `args` that hold the argument the loop computes | `invalid_argument` |
| two outputs on one device, whatever each calls it (an id and a role of the same motor); the message names the device id | `invalid_argument` |
| a `limit` that lies outside the range of `drives.arg` | `invalid_argument` |
| a command without `drives`, or whose `drives.arg` has no `minimum` and `maximum`, or a range that leaves out 0 | `unsupported` |

`duration_ms` above `max_loop_ms`, the robot's limit on a loop's life, is cut to it and reported in the plan's `clamps` (§0.2). A signal whose channel declares `max_rate_hz` under the loop's rate is sampled at the loop's rate and holds its value between the sensor's own updates; the plan names it in `notes`.

**What a loop reports** (`LoopReport`): `{state, reason?, guard?, runs_on, rate_hz, age_ms, remaining_ms, ticks, overruns, period_ms: {p50, p95, max}, signals: {<name>: {last, min, max, mean, integral, derivative}}, outputs: [{device, command, last, min, max, mean_abs, saturated_pct}], params, trace: {t_ms: [...], <signal name>: [...], out<i>: [...]}, notes?}`. The statistics cover the ticks since the previous report; `integral` and `derivative` are the signal's latest; `saturated_pct` is the share of ticks on which the output was cut. The trace is sampled at `trace_hz` and holds at most 200 points, the latest ones. Ticks earlier than the law's first are in neither. The tick that ends a loop is in both, with its reading and its outputs at 0, and always has a point in the trace.

**Why a loop ends** (`LoopEndReason`). The law itself ends a loop with `guard`, `input_lost`, `not_still` or, for a tick later than 10 periods, `overrun`; the others belong to whoever runs it. A step of a loop that has ended answers the same end, with the guard's name, and outputs at 0.

| reason | meaning |
|---|---|
| `completed` | `duration_ms` passed |
| `guard` | a guard held; `guard` is its name |
| `preempted` | it was stopped from outside |
| `unattended` | `attention_ms` passed with nobody supervising it |
| `overrun` | `rate_hz` could not be held; from the law: one tick came more than 10 periods late |
| `input_lost` | a signal's channel returned no value on 3 ticks in a row, while the loop settles or while the law runs |
| `not_still` | a `zero: {mean_ms}` measurement saw motion |
| `timeout` | a backstop behind the loop ended it |

**One law.** `packages/protocol/loop.ts` is the law. `packages/protocol/loop-golden.json` holds cases of `{spec, ctx, plan, ticks: [{set?, inputs, dt, expect: {outputs, guard?, end?, signals}}]}` that cover every term kind, zero mode, filter, guard and limit, a tick without a value, a dt of 0, a late tick and a param set in the middle of a ramp; its `note` says where each number comes from and what a port to Python 3.5 must mind; an implementation of the law in another language computes the same outputs from the same inputs, tick for tick, and is tested with the same file. The law therefore uses only + − × ÷, in a fixed order.

**Where it runs.** Every provider declares `loop: {runs_on, max_rate_hz}` or declares none; `describe_robot` reports it as `loop` (null when no provider of the robot runs loops).

| provider | `runs_on` | executor |
|---|---|---|
| stock EV3 | `host` | the runtime, in the server's process: one packet per tick carries every output refresh and every input read |
| twin | `host` | the same executor and the same provider over the simulated brick |
| ev3dev | `device` | the bridge on the brick (version 7): the loop is one task of its scheduler, reads and writes the sysfs attributes it holds open, and pushes telemetry to the computer every 0.5 s; the runtime builds the report from it |
| page hub | `host`, inputs only (`inputs: "pushed"`) | the runtime's executor; a tick answers each read from the latest pushed value, writes nothing and sends nothing to the page |

Declared `max_rate_hz`: stock EV3 50, twin 100, page hub 100, ev3dev 50 until probed: the provider's `probeLoop()` runs a plan's ticks back to back on the brick (real reads and the law, every output written as 0 and no run command, so nothing moves) and sets the link's `max_rate_hz` to the fastest of 10, 20, 25, 50, 100 and 200 Hz whose period holds the tick's 99th percentile twice over; a new link starts from 50 again. Each is a constant of its provider's transport; the hub's is the most messages a page may send in a second (§2.4), since no pushed value changes faster, and each pushed channel declares its own `max_rate_hz` (an imu: 20). The stock figure is conservative and not a measurement: no loop has run on a real brick (`docs/hardware-log.md`).

The devices a loop names decide the executor; the caller does not choose. A loop whose devices all belong to `host` providers runs in the runtime, at the lowest `max_rate_hz` among them. A loop whose devices all belong to one `device` provider runs on that device, at its `max_rate_hz`; the provider checks the plan before anything is sent (an ev3dev bridge older than version 7 is `misconfigured`, with the reinstall hint; a channel or a command its executor does not serve is `unsupported`). A loop that names a device of a provider without a loop, or devices of a `device` provider beside devices of another provider, is refused with `unsupported`.

**Page inputs.** A provider that declares `inputs: "pushed"` (the page hub) gives a loop signals and nothing else, and does not decide where a loop runs: `describe_robot`'s `loop` leaves it out, so a robot with no body is `loop: null`, and an EV3 or a twin with pages keeps its own rate. A signal reads a page's pushed `number` or `boolean` channel; a tick takes the latest value the page pushed, and a page that pushes more slowly than the loop's rate gives the same value on several ticks (the rule of a sensor slower than the loop, Planning). A tick has no value from a page that is not `active`, from a device that is down, from a channel that has pushed nothing yet or pushed null, and from a page silent for 300 ms (§4): three of those in a row end the loop with `input_lost`. Refused with `unsupported` at planning time, and nothing is sent: a page device as an output (a page moves nothing), a page channel that is not pushed, and a page device in a loop beside a device of a `device` provider (the page's values reach the computer, never that device).

**Rate.** `rate_hz` above the executor's `max_rate_hz` is refused with `invalid_argument`; the message names the maximum and where the loop runs. Nothing is slowed silently. A running loop that cannot hold its rate ends with reason `overrun`: 3 ticks in a row later than one period, or more than 5 % of the ticks of any second once a second has passed. The report counts the late ticks in `overruns`.

**Supervision.** `run_loop` plans the loop (devices, channels, `drives`, ranges, rate: everything is checked first, and a failed check sends nothing), starts it, and answers when the first 20 ticks have run or the loop has ended, whichever comes first. The robot is then `looping` and no call is in flight, so the model is free to think. `supervise_loop` is the one way in:
- it returns the loop's report: `state: running | ended`, the reason once ended, tick statistics, per-signal and per-output statistics since the previous report, and a trace sampled at `trace_hz`;
- `params` changes named numbers on a tick boundary (all of them on the same tick); `ramp_ms` (at most 10000 through the tool) moves them there linearly;
- `wait_ms` holds the call open until the loop ends or the time passes, so a caller with nothing to change waits in one call.

A report of an ended loop is answered once the robot has taken the path of `stop` after it (§1), so its `robot.activity` is `idle` or `fault`. After the end, `supervise_loop` keeps returning the final report, unchanged (its trace and statistics included), until the next `run_loop`; on a robot that has run no loop on this link it answers `illegal_state`, with `next` starting at `run_loop`.

The **attention window** makes supervision a duty: a loop ends with reason `unattended` when `attention_ms` have passed with no `supervise_loop` answered and none pending, counted from the answer of `run_loop`. A model that has moved on, or a person who interrupted it, therefore ends the loop.

Why not a blocking call for the whole loop: a model reads a result only when its call returns, so it could never steer a loop it is waiting on. Why not a model turn per tick: a turn takes seconds; a tick takes milliseconds.

**How the host executor ends a loop.** Beside the ends of the law: `completed` when the tick due at an age of `duration_ms` or more comes (it is not sent); `overrun` by the rule above; `input_lost` when a tick's exchange fails (no reply, a link that closed) or a signal's device leaves the registry; `preempted` when `stop` (or a cancelled call) reaches the runtime. `unattended` and `timeout` come from the process (§1). The first cause wins: a later one changes nothing.

**How a device executor ends a loop.** The device runs the law and its ends, `completed`, and `overrun` by the rule above, on its own clock; `stop` (or a cancelled call) asks it to end the loop with `preempted`, and `unattended` and `timeout` from the process ask the same with their own reason. The device brakes every driven motor first and then says how the loop ended; the first cause wins. An ev3dev bridge ends a loop with `timeout` after 1 s of silence from the computer (its watchdog), with `input_lost` when a held attribute cannot be read or written, and with `overrun` when it was itself held off the processor (once it runs again the late tick ends the loop; it writes no motor command on that tick). A device that does not say within `stop_worst_ms` that the loop ended is a failed brake (Safety, below). A link that closes ends the loop with `input_lost`.

**Safety.**
- Bounded: `duration_ms` ≤ `limits.max_loop_ms`, counted on the executor's own clock.
- Every end brakes every device the loop drives, first, ahead of any bookkeeping or output, and is then verified by the path of `stop` (§1). A brake that fails, or does not answer within `stop_worst_ms`, is named in the report's `notes`; the loop ends at that bound all the same, takes the verified stop, and leaves the robot in `fault` whatever the motors read.
- `stop` preempts a loop like any move and is verified.
- Guards run on the executor, on the tick that reads the signal.
- Link silence. Stock and twin: a tick whose packet is not answered ends the loop; the brick ends the motion `hold_ms` after the latest refresh, and the bridge page brakes every motor when its socket closes. ev3dev: the bridge's watchdog ends the loop after 1 s without a line from the computer, and the guard brakes every motor when the bridge is killed or, while a motor runs on power, 200 ms after the bridge last fed it. A page input: 300 ms after the page's last answer to a ping its values are ticks without a value, and the third ends the loop with `input_lost`.
- `hold_ms` of a motor output is at most 250 ms on stock firmware (`max_hold_ms` of its motor commands), so a loop that dies leaves a motor running for at most that long. On ev3dev a `power` output's is at most 200 ms, the guard's deadman behind it.
- No silent fallback anywhere: a rate, a device mix, a channel or a command the executor cannot honor is a typed refusal at planning time, and so is an output's fixed `args` entry that is not a param of its command or breaks the param's schema (`invalid_argument`).
- A stock provider's end brake overtakes every tick still waiting in the queue, and a tick planned while the loop ran carries no refresh once it has ended: the brake is the last command a driven port gets from the loop.

A loop whose link closes leaves the robot `offline`; calls then answer `robot_offline`, and the report is gone with the link.

## 6. The process

An MCP client starts it (`claude mcp add -s user spinecord -- bun <repo>/apps/local/main.ts`; `bun apps/local/main.ts --print-add` prints that command with the absolute path, quoted for the shells of the computer it runs on; on Windows the separator is printed as `"--"`). stdout carries JSON-RPC only; every log line is one JSON object on stderr. With `--log-file <path>` each of those lines is also appended to that file, written when it is logged, so the lines of a process that ends are in it. The path follows the rule of every path on the command line (absolute as it is, a leading `~` the home folder, relative from the repository root); the file's folder is created; a file that cannot be opened ends the start with exit code 1 and the path on stderr. A write to the file that fails while the server runs (a full disk) stops nothing: the file is given up, one `{"ev":"log_file_failed","path","error"}` line goes to stderr, and the server serves, stops its robots and exits as without the flag. `--print-add` carries the flag with the absolute path.

**Call log.** Every `tools/call` writes one line to stderr when it is answered:

```json
{"ev":"call","ts":"2026-11-22T08:19:28.089Z","tool":"drive","robot_id":"r1-sim","ok":true,"code":null,"reason":"completed","ms":350,"trace_id":null,"moved":true}
```

| field | value |
|---|---|
| `ts` | when the call was answered, ISO 8601 UTC |
| `tool`, `robot_id` | as the caller sent them, cut at 64 characters; null when absent |
| `ok`, `code` | the envelope's `ok`; the error code when `ok` is false, else null |
| `reason` | the result's `reason` (why a move or a wait ended); `run_program` gives its `outcome`; null when the result has none |
| `ms` | how long the call took in the process |
| `trace_id` | the id of an `internal` error behind this answer, else null |
| `moved` | true when a moving operation was sent to the robot during the call, or may have been (a call the backstop ended); false when nothing was sent, as for a refused argument or `busy` |

`run_loop` and `supervise_loop` write the call line of every tool; its `reason` is the report's `reason` (null while the loop runs) and `moved` is true for `run_loop` once the loop has started. The end of a loop, whoever caused it, writes one more line: `{"ev":"loop_end","ts","robot_id","reason","guard","runs_on","ticks","overruns","ms"}`. It holds no signal value and no trace.

The line never holds arguments, result data or images. An `internal` error (§7) also writes `{"ev":"internal","ts","trace_id","tool","robot_id","message","stack"}` with the stack of the failure and of what caused it, cut at 4000 characters; the `trace_id` is the one in the error's message, and in a program step's `error.trace_id` when a step failed that way. To find a call: `grep '"ev":"call"'` on the server's stderr or its `--log-file`, then filter on `robot_id`, `ok` or `trace_id`.

**Robots.** Chosen on the command line or in a config file (`bun apps/local/main.ts --help` lists every option). Without arguments: the twin of the example robot (`deployments/example/robots/r1.json`) in `apps/local/examples/room.json`. `--twin`, `--ev3` and `--ev3dev` without a robot file use that example robot. A relative path on the command line is taken from the repository root, one in a config file from that file's folder; the working directory of the process decides nothing. A file that is not there ends the start with its absolute path.

| source | runtime's providers | link |
|---|---|---|
| `twin` | simulated brick + the real EV3 provider + `sim.world` (§4 Twin), world from a JSON file | online from start |
| `ev3dev` | ev3dev provider over the system `ssh` client | `offline` at start, `online` when a link passes the handshake (§1); the process starts and serves its other robots whether or not the brick answers. `offline` when the ssh process ends, `online` again when a new link passes the handshake |
| `ev3` | the real EV3 provider over a byte transport: the bridge page in Chrome or Edge passes WebHID reports to one WebSocket on `127.0.0.1` | `offline` until the page has an EV3 open, `offline` again when the page, the cable or the brick goes |
| `pages` | the page hub alone | online from start, with zero devices until a page joins |

With pages enabled, every other robot gets a page hub as its last provider too.

**Pages.** `--pages [robot.json]` adds a robot of source `pages` (id `<profile.id>`; without a file, the example `deployments/example/robots/pages.json`) and enables pages for every robot of the process. `--page-port <n>` (default 8768; 0 takes a free port, which `join` names) is the port of the page listener. `--lan` adds the network listener, `--lan-interface <name|address>` picks its interface, `--lan-cert <cert.pem> <key.pem>` gives it a certificate of the person's own and `--lan-host <name>` the name that certificate is for; `--page-origin <https origin>` adds the tunnel listener (all below); `--page-ext <folder>` serves that folder's `.js` files as extensions of the page. Each needs `--pages`, the `--lan-*` flags need `--lan`. In a config file: `"pages": {"port"?, "lan"?: true | {"interface"?, "cert"?, "key"?, "host"?}, "origin"?, "ext"?}` enables them, and `{"source": "pages", "robot": path, "id"?}` is such a robot (it enables them too).

**Page listener.** Bound when pages are enabled: `127.0.0.1` by name, on its own port, apart from the bridge page's listener; a taken port ends the process with a message; nothing of it listens beyond loopback. It serves the page (`/`, `apps/peripheral-page`) and its files (`page.js`, `page.css`, `level.js`), the extensions (`/ext/<file>`: only a name of the `.js` files directly in the `--page-ext` folder, listed at each request; anything else is 404; the page loads them as module scripts after its own), the pairing console (`/console`), and accepts the page socket (`/page`). It answers a request only when its `Host` is this listener's own (`127.0.0.1:<port>`, `localhost:<port>`), with 403 otherwise, and accepts a socket only when the `Origin` is too (`http://127.0.0.1:<port>`, `http://localhost:<port>`), with 403 otherwise; then it requires the token in the hello. This listener gives a page the token without a link: it writes it into the HTML it serves (`<meta name="spinecord-token">`), since whoever reaches a loopback listener with a loopback `Host` is on this computer. The `Host` check also refuses a page of another site whose name was made to resolve to this computer. On this computer the page is a secure context without a certificate. The page is served with `Content-Security-Policy: default-src 'self'; connect-src 'self'` and a `Permissions-Policy` that allows the camera, the microphone and motion sensors on `self` only.

**Network listener (`--lan`).** Off unless the flag is given; without it nothing of the process listens beyond loopback. With it the process binds one more listener, TLS only (HTTPS and WSS: a phone's page is a secure context only so), on the address of one interface (never the wildcard address), port `--page-port` + 1. The interface is the one `--lan-interface` names (by name or address), else the only one with a private IPv4 address (10/8, 172.16/12, 192.168/16), else the one of those the default route leaves from; when none fits, the start ends with exit code 1 and a message that lists the interfaces. The listener's name is `a-b-c-d.local-ip.sh` for the address a.b.c.d: a public DNS service answers that name with that address and publishes a wildcard certificate for `*.local-ip.sh` and its private key. The process fetches both at start (`https://local-ip.sh/server.pem` and `/server.key`, bounded to 8 s), checks that the key belongs to the certificate, that the certificate covers the name and is valid at start, and caches them in the computer's cache folder (`spinecord/lan-cert.json`, with the certificate's expiry) until the certificate expires. With `--lan-cert` the process serves the person's certificate and fetches nothing, under the interface address when it names that address, else under `--lan-host` or its only DNS name. When no certificate can be had, the start ends with exit code 1 and a message that names `--lan-cert`. At start the process asks this computer's resolver for the name and says on stderr whether it resolves to the address (a resolver with rebinding protection strips such answers). The listener serves the page (`/`) without the token, its files (the extensions among them) and the socket, and nothing else; it answers only when `Host` is `<name>:<port>`, with 403 otherwise, and accepts a socket only when `Origin` is `https://<name>:<port>`. The private key of the service's certificate is public: TLS there gives a secure context, not secrecy from someone on the same network, and the token is what keeps a stranger from joining.

**Tunnel listener (`--page-origin <https origin>`).** For a person who runs a tunnel of their own (cloudflared, pinggy). Off unless the flag is given. The process binds a third listener on `127.0.0.1`, port `--page-port` + 2, plain HTTP, for the tunnel program to forward to. It serves what the network listener serves (no console, no token) and answers only when `Host` is that origin's host and, for the socket, `Origin` is that origin. Every frame and transcript of a page that joins through it crosses the tunnel's operator: the process says so on stderr at start.

**Pairing token.** 128 random bits, made at each start, never written to a file or a log line, and sent by the page in its hello. A page on the network or tunnel listener has it from its join link's fragment, which a browser does not send in a request: `https://<name>:<port>/#t=<token>&robot=<id>` (or `<origin>/#t=…`). Wrong tokens are counted per listener and remote address: after 5 within a minute that address is refused for a minute (4029), whatever it sends. On the tunnel listener every peer is the tunnel program on `127.0.0.1`, so the refusal holds for every page of the tunnel. At most 8 pages per process.

**Showing the link.** With `--lan` or `--page-origin`, the process writes to stderr (never to `--log-file`) each join link with the same link as a QR code drawn in text, once per robot. The pairing console (`http://127.0.0.1:<port>/console`) shows the same links as QR codes, the result of the name check, and the pages that joined. It is served by the loopback listener only, so neither `--lan` nor a tunnel publishes a link or a code.

**Joining a page.** `list_robots` carries, per robot, `join`: one sentence for a person ("On this computer open http://127.0.0.1:8768/ in Chrome or Edge and lend robot r1-sim the devices of that page."; with `--lan` it adds the network address and the console, where the link with the token is), or null when pages are off. `join` never holds the token.

**Page log.** One line per transition of a page: `{"ev":"page","ts","robot_id","name","from","to","why","kinds":[…]}`. It holds device kinds, never a value, a frame, a transcript or the token.

**Bridge page.** `apps/robot-page/bridge.html` runs no runtime and no timer on the path of a command: a browser fires the timers of a hidden or covered window once per second, and delivers socket messages and HID reports at once. The 10 ms `until` watch therefore runs in the process (measured: `apps/local/bench/results/hidden-page.json`). The process binds `127.0.0.1` by name, only when an `ev3` robot is configured, on a fixed port (default 8767; WebHID permission belongs to the origin); a taken port ends the process with a message. The socket accepts only the page the process serves, and one page: a second tab is closed with code 4009 and the reason "another tab already holds the robot", which that tab shows. The process tells the page it holds the robot (`{"t":"accepted"}`); when that socket closes, the page brakes every motor port by itself. A refused tab sends the brick nothing.

**Ending.** When stdin closes (the client went away) or the process receives SIGINT, SIGTERM or SIGHUP, every robot of the process first enters `closing` (life `serving → closing → closed`), in which every call answers `robot_offline` with `retryable: false` and a message that the server is shutting down; then it stops every online robot (verified, bounded by `stop_worst_ms`), writes one `{"ev":"stopped","robot_id","motors_stopped"}` line per robot on stderr, and exits. A process that is killed outright stops nothing itself: a stock EV3 is then braked by the bridge page, an ev3dev brick by its bridge (the ssh link closed, or 1 s of silence) or, if the bridge is dead too, by the guard process (§0.8).

**3D view (`--view`).** Off unless the flag is given (`--view-port <n>`, default 8769, 0 takes a free port; in a config file `"view": true | {"port"?}`); it needs a twin, and a start with `--view` and no twin ends with a message. The process binds `127.0.0.1` by name, on its own port, and says its address on stderr; a taken port ends the process with a message. It serves the page (`/`, `apps/twin-view`) and its files (`view.js`, `view.css`), answers only when `Host` is its own (`127.0.0.1:<port>`, `localhost:<port>`), with 403 otherwise, and accepts the page socket (`/ws`) only when `Origin` is too. Over the socket it sends each twin's world, its pose and the state of its brick (motors, ports with the values of each sensor's mode, LED, screen, buttons, battery) about 30 times a second, each tone of the brick, each phrase of `sim.speaker`, and each tool call as it begins (with its arguments, cut to 600 characters of JSON, never through a character) and as it ends (with its summary line and its error code), each with the time it happened. The values it shows are what the robot would read without noise (a colour sensor's spot average, not the colour under its centre) and spend nothing of the world's noise. Motion noise is drawn per 20 ms of world time from the seed, not per physics step, so the steps a watching page cuts change neither the noise a robot gets nor its path by more than 0.05 mm: watching never changes what a robot reads. The person at the page may act on a twin as on a robot on the floor: carry it to another pose (a gyro counts the turn; a robot without one does not feel it; a pose that overlaps something is refused), set a box down inside the arena, move one or take one away (a box on the robot is refused), restore the obstacles the world came with and the start pose, and hold the brick's buttons down; a button is down while any page holds it, and a page that goes away lets go of the buttons only it held. An action that cannot be done changes nothing and is answered with its reason (`does_not_fit`, `box_on_robot`, `outside`, `no_such_box`, `too_fast`, `invalid`, `internal`). A page's message is at most 2 KB and its actions at most 60 a second (letting a button go always passes); a longer message closes that page's socket only; a page that falls behind misses state frames rather than queueing them, and is closed past 4 MB unread, to join again with a fresh state. Nothing of it changes a tool's semantics: the runtime and the EV3 provider talk to the simulated brick as before. Hardware robots are not shown.

## 7. Envelope and error codes

`Envelope<T>` in types.ts: `{ok, robot?, data | error, next}`; `robot` is `{id, backend, link, activity}`, with `backend` null while the robot is offline. `backend` is an open string that the robot's first provider declares: `ev3-stock`, `ev3dev`, `sim`, `page`; a twin is the robot whose `backend` is `sim`; `error` is `{code, message, retryable, retry_after_ms?, measured?}`, with `measured` present when the watch of a condition ended a move and the wheels could still be read (§4). An error that ends a move any other way (the link closed mid-drive, the backstop) carries none: read the robot. `isError: true` when `ok:false`. Every result (success and error) carries the envelope as `structuredContent`, and every tool advertises its `outputSchema` (`ToolDef.output` in tools.ts: the envelope with that tool's `data` shape; object root, open objects, minimal `required`, so one schema accepts both outcomes). Every result validates against it; a result that does not is a JSON-RPC error, never sent as data. For clients without structured output, one `text` block repeats it: line 1 is a one-line summary, the last line is the envelope as single-line JSON. Plus one `image` block when an image channel was read. Clients that write code against the tools: `docs/code-mode.md`.

**One shape per kind of answer.** `data` is an object in every tool, never a bare array, and a thing has one name wherever it appears:

| what | field | tools |
|---|---|---|
| channel values | `readings: [{device, channel, value, unit?, ts, error?, absent?}]`, one per channel; an image channel's reading is `{device, channel, value: null, image: true, mime, age_ms, ts}` | `read_device` `read_all` `wait_until` |
| the robots | `robots: [{id, backend, link, activity, fault_reason, connect, join}]` | `list_robots` |
| a command's result | `{requested, applied, measured, clamped, clamps?, reason, note?, ms}`; `clamps: [{arg, requested, applied, target}]` when the runtime cut an argument (§0.2); `note` when a drivetrain target is under the smallest move and nothing was sent (§4) | `drive` `turn` `arc` `command_device` |
| the readings that met `until` | `readings`, the shape above, present when `reason` is `condition_met`: a read made after the stop differs from them by the sensor's noise | `drive` `turn` `arc` `command_device` |
| what a drivetrain move measured | `measured: {distance_cm, heading_change_deg, source, left_deg, right_deg, heading_error?}`; `source` is `gyro` (the drivetrain's `heading` channel, §3) or `encoders`; `heading_error` says why a declared heading did not measure the move (§3) | `drive` `turn` `arc` |
| how long the call took | `ms` | `read_all` `wait_until` `drive` `turn` `arc` `command_device` `run_program` |
| why a call ended | `reason` | `wait_until` (`condition_met`, `timeout`, `preempted`) and every command result (`StopReason`) |
| a loop's report | `LoopReport` (§5a); `reason` is why the loop ended (`LoopEndReason`) | `run_loop` `supervise_loop` |
| the pages of a robot | `pages: [{name, state, why?, devices: [ids], unavailable: [{kind, why}], last_seen_ms}]`, present when pages are enabled; `last_seen_ms` is how long ago the page last answered | `describe_robot` |
| how a person adds a page | `join` (string \| null) per robot | `list_robots` |

**`reason` of a command result.** `completed`: the whole request was done; `clamped` may be true beside it when an argument that is not the target was cut. `clamped`: the target was cut to a limit and the shorter target was reached. `condition_met`: `until` ended it. `stalled`, `preempted`, `timeout`: it ended early, and `measured` says how far it got. A caller tests `reason`, never `clamped`, to know whether a move did what was asked.

**`next` after an error.** An error whose fix is another tool names that tool first: a condition on a channel that is not active names `read_device`, then the same tool. Otherwise a retryable error and `invalid_argument` name the same tool first. `busy` then names `read_all` and `stop`: the call in flight ends by itself, and `stop` ends it early; a robot that is `looping` names `supervise_loop` and `stop`. The end of a loop is data (`reason`), never an error: `invalid_argument` covers a rate above the executor's maximum and a loop spec that fails validation (the message names the field); `unsupported` covers a robot with no loop executor, a device mix no executor covers (a page beside a `device` provider among them), an output command without `drives`, a page device as an output, and a page channel that is not pushed; `busy` covers a second loop and a moving call during a loop; `illegal_state` is `supervise_loop` on a robot that has run no loop on this link. `illegal_state` names `read_all`: the robot is not in `fault` and takes every other tool. `unsupported` from `drive`, `turn` or `arc` names `describe_robot`, then `command_device`: the robot's actuators are its devices. A moving call that failed after it started names `read_all` first (§1). `device_offline` names `describe_robot` (its `pages` say which page sleeps and why), then the same tool. `unknown_device` remains the answer for a page that is `gone`. A capability the browser lacks is never an error at call time: the command or the device is absent from the manifest, and `describe_robot.pages[].unavailable` says why.

| code | retryable | meaning |
|---|---|---|
| unknown_robot / unknown_device / unknown_channel / unknown_command | no | name not found; message lists valid ones |
| unsupported | no | drive, turn or arc on a robot without a drivetrain, or whose drivetrain's pair device is not attached; a command the brick's hardware cannot do |
| invalid_argument | no | names field, schema rule, allowed range |
| robot_offline | yes · while the process shuts down: no | the robot's link is `offline` or closed during the call (§1). A call to a robot that is already `offline` carries `connect` in its message; a call the link closed under carries the driver's reason |
| busy | yes | activity is acting/running_program/looping/stopping; `retry_after_ms` |
| illegal_state | no | names current state and allowed tools |
| fault | no | use reset_fault after inspecting; a new link's verified stop also clears it (§1) |
| stop_unverified | no | robot is now in fault |
| timeout | yes · moving calls: no | an answer did not come in time, in one of two ways, and the message says which. The call outlived the process's backstop (§1) and was aborted; robot state included. Or a brick did not answer one exchange within its driver's reply time (a lost reply: `ev3 no_reply`, `ev3dev: no reply`); a lost reply does not by itself close the link, and a link that is gone answers `robot_offline`. A read that lost its reply changed nothing and may be sent again. A moving call that lost a reply answers `retryable: false` with `next` starting at `read_all` (§1): the operation may have run on the brick, where it ends at its time bound. A tool's own time limit is never this error: it ends the call with data (`reason: "timeout"`, `met: false`, `outcome: "timeout"`). A move that timed out may have partly happened and was stopped: read the robot before moving again |
| stale_image | yes | frame older than 1500 ms |
| condition_unreadable | no | a channel named by a condition (`until`, `wait_until`, a program's `while`, `if` or `success`) returned no value in 3 polls in a row, so the condition cannot be evaluated (§4); the message names the channel, the count and the reading's error. A move the condition guarded was ended and braked there, and `error.measured` holds what it had done. Never for a `null_when_absent` channel (§2.2) |
| device_offline | yes | the device is in the registry and cannot answer: its page is hidden, locked, paused by the person, or silent, or the device is down. `retry_after_ms` is 2000 and the message says what the person at the page must do. The robot's other devices work |
| internal | no | an unexpected failure (a malformed reply from a brick, a bug); the message carries it, with a `trace_id` under which the process's log has the stack (§6, Call log) |

`misconfigured` (no) is what a provider or the runtime throws for a bad configuration. At start it ends the process. When an `ev3dev` link is opened again it fails that attempt: the robot stays `offline`, the attempt is repeated, and `connect` carries the reason (§1). `ErrorCode` in types.ts has these codes and no other, and they are the `code` enum of every output schema. `RETRYABLE` in types.ts is the one list of the codes a caller may send again; the runtime and the drivers read it.

## 8. Tools

`TOOLS` in `tools.ts`, served with `SERVER_INSTRUCTIONS`:

| group | tools |
|---|---|
| discover | `list_robots` `describe_robot` `describe_device` |
| sense | `read_device` `read_all` `sample_device` `wait_until` |
| act | `drive` `turn` `arc` `command_device` `stop` `reset_fault` |
| programs | `run_program` |
| loops | `run_loop` `supervise_loop` |

`run_loop` and `supervise_loop` are not program calls: a program is a sequence in the server's process, a loop is a law on an executor.

No tool is for pages alone. A page device is found with `describe_robot` and `describe_device`, read with `read_device`, `read_all`, `sample_device` and `wait_until`, commanded with `command_device`, and named in `until` and in programs.

- `list_robots` returns the robots of the process: `{robots: [{id, name, backend, link, activity, fault_reason, connect, join}]}`; `name` is the robot's name (§3) or null, and `describe_robot` gives it too; `connect` tells what a person must do to bring an offline robot online, `join` how a person lends it a page's devices. It is the one tool that addresses no robot, so its envelope has no `robot`.
- Every other tool takes `robot_id` and runs under the state of §1; the runtime executes it (§4).
- `request_id` is optional on the tools that take it and is a label (§0.5).
- A tool that moves the robot is annotated `idempotentHint: false`.
- Defaults are stated in the description of their argument: `speed_pct` 30, `rate_hz` 10 (`sample_device`), `poll_hz` 20 (`wait_until`), `direction` forward (`arc`).
- `read_device` without `channels` reads the device's active non-image channels; an image channel or one that needs a mode switch is read only when named (§2.2).
